# P2-02 语义增强搜索设计

版本：V1.0
日期：2026-07-23
状态：等待设计审核
所属路线图步骤：P2-02 语义增强搜索
前置条件：P2-01 数据清理、安全删除与完整性检查已完成人工复核

## 1. 目标

在不改变现有普通搜索行为的前提下，为原子事件、因果关系和具体案例三个列表增加由用户主动触发的本地语义增强查询。

本阶段使用固定的本地嵌入模型和 PostgreSQL `pgvector`：

1. 识别名称或描述不同、但语义相近的记录；
2. 将普通匹配与语义候选合并，普通匹配保持优先；
3. 不向用户展示匹配原因、相似度或检索实现细节；
4. 为 P2-03 批量导入的疑似重复发现提供可复用能力；
5. 保持普通搜索在模型下载、索引重建或 Worker 故障时始终可用。

## 2. 范围

### 2.1 包含

- 原子事件、因果关系和具体案例列表的“增强查询”入口；
- 普通搜索与语义候选的服务端合并、去重、排序和分页；
- 独立“参数配置”标签页；
- 两个固定版本的本地中英文嵌入模型；
- 手动首次下载、下载进度、文件校验和离线复用；
- 模型切换确认、自动下载、自动加载和自动全量索引；
- 每个模型独立的相似度门槛；
- PostgreSQL `pgvector` 和 HNSW 索引；
- 独立 TypeScript 语义任务服务；
- 全量索引、增量向量更新、失败重试和服务重启恢复；
- 真实模型烟雾测试、固定语义质量测试集和十万条数据性能基准。

### 2.2 不包含

- 批量导入和公开录入接口；
- 创建或编辑表单候选下拉列表的语义匹配；
- 因果图中心事件的语义搜索；
- 外部 AI、外部嵌入 API 或 Python 模型服务；
- 用户自定义模型、模型地址或 Hugging Face 仓库；
- 同时保存多个模型的业务向量；
- 搜索历史、搜索日志或行为分析；
- 匹配原因、相似度、语义标签或调试信息展示；
- 重排序模型、混合权重或高级检索参数；
- 自动创建、自动合并或自动修改业务数据；
- 移动端专项适配。

## 3. 已确认决策

- 现有普通搜索保持不变，继续随搜索框内容自动查询。
- 增强查询只在用户点击“增强查询”后执行。
- 三个主列表使用相同的增强查询交互。
- “增强查询”紧邻搜索框右侧。
- 普通匹配排在语义新增结果之前。
- 语义候选最多 100 条，最终结果仍按每页 50 条分页。
- 不展示匹配原因和相似度，不记录搜索日志。
- 搜索内容改变后立即退出增强模式，恢复普通搜索。
- 新增独立“参数配置”标签页，放在“数据维护”和“系统状态”之间。
- 使用两个固定内置模型：“轻量快速”和“质量优先”。
- 默认选中“轻量快速”，首次进入时不自动下载。
- 所有已下载模型文件都保留，切换模型不删除旧模型文件。
- 数据库只保留当前模型生成的业务向量。
- 不提供“是否开启增强查询”开关。
- 首次下载完成后自动加载并生成全量索引。
- 切换模型前二次确认；确认后立即删除旧向量，必要时下载新模型，并自动加载和索引。
- 增强查询按钮始终可以点击；不可用时说明具体原因并保留普通查询结果。
- 相似度门槛可配置，复用创建因果关系页面的置信度组件。
- 每个模型分别保存自己的相似度门槛。
- 模型下载和向量生成在独立 TypeScript 服务中执行。
- 向量保存在现有 PostgreSQL 的 `pgvector` 中，不增加独立向量数据库。
- P2-02 期间只保留必要的本地提交，不推送 GitHub。

## 4. 模型设计

### 4.1 内置模型

| 档位 | 模型仓库 | 固定提交 | 格式 | 向量维度 | 主要模型文件 | 用途 |
| --- | --- | --- | --- | ---: | ---: | --- |
| 轻量快速（默认） | `Xenova/multilingual-e5-small` | `761b726dd34fb83930e26aab4e9ac3899aa1fa78` | ONNX INT8 | 384 | 约 118 MB | 普通 CPU 快速检索 |
| 质量优先 | `onnx-community/bge-m3-ONNX` | `25b9af8e87a38eb120cfe87125383677b9cd309e` | ONNX INT8 | 1024 | 约 568 MB | 更高质量的中英文和混合语义检索 |

下载总量还包含 tokenizer、配置文件和校验元数据，页面显示内置清单计算出的预计总下载大小。

两个模型都必须：

- 支持中文、英文和中英混排；
- 由 Transformers.js 在服务端 CPU 上运行；
- 使用固定提交和固定文件清单；
- 使用应用内置的模型适配器定义 query/document 前缀、池化、归一化和最大输入长度；
- 不允许用户替换为任意下载地址。

### 4.2 相似度门槛

- 每个模型保存独立门槛；
- 初始值通过固定语义质量测试集校准为中等强度，不直接复制另一个模型的数值；
- 参数配置页复用因果关系置信度组件的交互和样式；
- 修改门槛只影响后续查询过滤，不重新生成向量或重建 HNSW；
- 普通查询结果不受门槛影响。

## 5. 向量文本

向量文本由服务端根据最新业务记录确定性生成。

### 5.1 原子事件

按以下顺序组合：

```text
事件名称：<name>
别名：<aliases>
关键词：<keywords>
说明：<description>
```

空字段不写入。别名和关键词使用稳定顺序，避免仅因返回顺序变化重复生成向量。

### 5.2 因果关系

```text
原因事件：<cause event name>
结果事件：<effect event name>
关系说明：<description>
```

不包含关联具体案例内容，避免案例数量改变关系本身的语义表达。原因或结果事件更名时，必须为引用该事件的关系创建增量更新任务。

### 5.3 具体案例

```text
具体案例：<content>
```

### 5.4 查询文本

- 查询使用用户当前输入内容；
- 模型适配器负责加入模型要求的 query 前缀；
- 文档适配器负责加入模型要求的 document/passage 前缀；
- 输出使用归一化后的稠密向量；
- 超过模型输入上限时按确定性规则截断，名称和结构字段优先于自由说明。

## 6. 运行架构

### 6.1 服务职责

新增独立 TypeScript 语义任务服务：

```text
Web -> API -> PostgreSQL/pgvector
              |
              +-> Semantic Worker -> 本地模型持久化卷
```

API 负责：

- 参数配置公开 API；
- 模型状态和任务进度读取；
- 创建下载、切换和重试任务；
- 增强查询普通匹配、向量检索、合并和分页；
- 业务写事务中的增量任务登记；
- 将查询文本发送给 Worker 的内部推理接口。

Semantic Worker 负责：

- 下载、校验和缓存模型；
- 加载当前模型并复用推理实例；
- 提供容器内部查询向量接口；
- 全量和增量业务向量生成；
- 任务重试、恢复和进度更新；
- 模型切换或进程退出时释放推理资源。

### 6.2 部署

- Docker Compose 增加独立 Worker 服务；
- Worker 与 API 使用同一代码仓库和 TypeScript 技术栈；
- 模型目录使用独立 Docker 持久化卷；
- Worker 内部端口不映射到宿主机；
- API 普通健康状态不依赖 Worker 就绪；
- Worker 不可用时普通应用和普通搜索继续工作。

## 7. 模型生命周期

### 7.1 首次使用

1. 参数配置页默认选择“轻量快速”；
2. 页面显示预计下载大小和“下载并使用”；
3. 用户手动点击；
4. Worker 下载到临时位置并持续保存进度；
5. 文件清单和校验值全部通过后原子移动到正式模型目录；
6. Worker 自动加载模型；
7. 系统自动创建全量索引任务；
8. 全部记录完成并校验后将索引标记为“可用”。

### 7.2 切换模型

切换前确认框说明：

- 当前索引将被删除；
- 新索引完成前增强查询不可用；
- 新模型未下载时需要下载；
- 待下载模型的预计大小。

用户确认后：

1. 锁定模型切换入口；
2. 停止使用并删除旧业务向量；
3. 释放旧模型；
4. 新模型未下载时自动下载并校验；
5. 加载新模型；
6. 自动执行全量向量生成；
7. 完整性校验通过后发布新索引；
8. 解锁模型切换入口。

旧模型文件始终保留，但旧模型业务向量不保留。

### 7.3 关闭和重启

- 不提供增强查询开关；
- 服务重启后根据数据库当前模型、任务状态和本地文件重新恢复；
- 已下载且索引一致时直接加载当前模型；
- 遗留的执行中任务经租约判断后重新排队；
- 不把临时文件或未完成索引误判为可用。

## 8. 状态与交互

### 8.1 参数配置页

“参数配置”位于“数据维护”之后、“系统状态”之前。本阶段只有“语义增强查询”配置区，显示：

- 两个内置模型及用途；
- 当前使用和已下载标识；
- 下载、校验、加载和索引状态；
- 下载进度；
- 索引已处理数量和总数量；
- 最近完成时间；
- 失败错误摘要和重试入口；
- 当前模型相似度门槛。

状态至少包括：

```text
未下载
下载中
正在校验
正在加载
正在生成索引
可用
下载失败
索引失败
```

同一时间只允许一个模型下载或全量索引任务。全量任务期间禁止再次切换模型。

### 8.2 三个列表

原子事件、因果关系和具体案例列表保持一致：

- 搜索框右侧增加“增强查询”；
- 高度、间距、圆角和 loading 状态遵循现有紧凑控件；
- 普通搜索继续自动触发；
- 点击增强查询后避免重复提交；
- 成功后从结果第一页显示；
- 修改搜索内容后立即恢复普通查询；
- 翻页和页码跳转继续回到列表顶部；
- 详情跳转和返回定位机制保持现状；
- 页面刷新不恢复上一次增强模式。

### 8.3 不可用提示

增强查询按钮始终可点击。API 每次执行前检查当前状态：

| 状态 | 行为 |
| --- | --- |
| 搜索内容为空 | 提示“请先输入搜索内容” |
| 没有当前模型 | 提示“尚未下载并使用语义模型” |
| 正在下载 | 提示“模型正在下载，增强查询暂不可用” |
| 正在加载或索引 | 提示“语义索引正在生成，增强查询暂不可用” |
| 任务失败 | 显示简短原因和“前往参数配置”入口 |
| Worker 不可用 | 提示“语义服务暂不可用” |
| 索引可用 | 执行增强查询 |

提示使用应用现有短暂错误样式。失败不清空列表、不改变普通查询结果和当前分页。

增量索引处理中允许查询已完成索引，但提示：

```text
语义索引更新中，结果可能暂不包含最新修改
```

## 9. 查询和排序

### 9.1 查询流程

1. API 校验非空查询、当前模型和索引状态；
2. API 请求 Worker 生成查询向量；
3. PostgreSQL 查询当前数据类型中达到门槛的前 100 条语义候选；
4. PostgreSQL 同时按现有逻辑计算普通匹配；
5. 服务端合并并按业务 ID 去重；
6. 普通匹配保持现有顺序并整体优先；
7. 仅由语义检索新增的记录按相似度降序；
8. 合并结果按每页 50 条返回；
9. 前端沿用当前列表渲染。

### 9.2 展示约束

前端不展示：

- 普通或语义来源；
- 相似度分数；
- 匹配字段；
- 匹配原因；
- 查询耗时或内部模型信息。

语义相似度只用于服务端过滤和排序。

## 10. 数据设计

### 10.1 `semantic_model_settings`

每个内置模型一行，保存：

- 模型代码；
- 固定版本；
- 下载和校验状态；
- 相似度门槛；
- 最近下载、最近使用和最近错误信息。

模型仓库、文件名、维度、池化和校验值以应用白名单为准，不能由数据库或客户端任意覆盖。

### 10.2 `semantic_index_state`

全局单行状态，保存：

- 当前模型代码；
- 模型加载状态；
- 索引状态；
- 总数量和已完成数量；
- 待处理增量数量；
- 最近成功时间；
- 最近错误摘要；
- 状态版本。

状态版本用于防止旧任务在模型切换后回写新状态。

### 10.3 `semantic_embeddings`

保存：

- 数据类型；
- 业务记录 ID；
- 当前模型代码；
- 源内容 SHA-256；
- 不定维 `vector` 数据；
- 生成时间。

同一数据类型和业务 ID 唯一。通过模型代码、数据类型和维度转换建立部分 HNSW 余弦索引，分别支持 384 和 1024 维。

### 10.4 `semantic_jobs`

保存：

- 下载、全量重建或增量更新类型；
- 模型代码；
- 等待、执行、完成或失败状态；
- 总数量和已完成数量；
- 尝试次数；
- 租约和执行者标识；
- 错误摘要；
- 创建、开始和完成时间。

同一业务记录的待处理增量任务必须合并，只保留最新内容对应的工作。

## 11. 数据同步和一致性

### 11.1 业务写入

- 创建或修改业务记录的事务同时登记增量任务；
- 业务保存不等待模型推理；
- Worker 执行前重新读取最新业务数据；
- 修改记录后旧向量立即失效；
- 删除记录时同步删除向量和尚未执行的增量任务；
- 事件更名时，为该事件及所有引用它的因果关系登记更新任务。

### 11.2 防止旧任务覆盖

Worker 写入前必须检查：

- 当前活动模型仍与任务模型一致；
- 状态版本未变化；
- 业务记录仍然存在；
- 当前源内容哈希仍与生成输入一致。

任何条件不满足时丢弃本次结果或重新排队，不允许旧结果覆盖最新业务内容。

### 11.3 全量发布

- 全量索引使用稳定批次处理；
- 单条失败记录错误并按限制重试，不永久卡死整个进度；
- 全部记录处理完成后重新核对三类记录数量、模型代码和源内容哈希；
- 只有校验通过才把索引状态设为“可用”；
- 模型切换或全量重建期间增强查询整体不可用。

## 12. API 设计边界

### 12.1 公开 API

增加语义配置端点，支持：

- 获取模型目录、当前模型、门槛和任务状态；
- 首次下载并使用模型；
- 确认切换模型；
- 修改指定模型门槛；
- 重试失败任务。

现有以下列表端点增加增强查询模式，不复制三套列表实现：

```text
GET /api/events
GET /api/relations
GET /api/cases
```

普通模式的请求和响应保持兼容。增强模式沿用现有搜索词、孤立过滤、事件过滤和分页参数。

增强不可用使用稳定业务错误码区分原因，前端不解析自由文本决定行为。

### 12.2 内部 API

Worker 提供只在容器网络内可访问的查询向量接口：

- 只接受当前活动模型和受限长度的查询文本；
- 只返回归一化向量和模型状态；
- 不接受任意模型路径或下载地址；
- 不映射宿主机端口；
- 不写入公开 OpenAPI 文档。

## 13. 下载与运行安全

- 模型清单由应用白名单定义；
- 固定仓库、提交、文件名、大小和 SHA-256；
- 下载使用临时目录；
- 校验通过后原子移动；
- 所有目标路径都由模型代码解析，不拼接用户输入；
- 模型持久化卷与 PostgreSQL 备份分开管理；
- 数据库备份只需要保留模型代码、状态和业务向量；
- Worker 内部接口设置请求大小、超时和并发限制；
- 下载或 Worker 故障不能降低普通 API 的可用性。

## 14. 错误与恢复

- 下载失败：保留错误摘要和可重试状态，不发布模型；
- 校验失败：删除无效临时文件，不覆盖已有完整模型；
- 模型加载失败：增强查询不可用，普通查询继续；
- 全量索引失败：不标记可用，允许从安全批次重试；
- 增量任务失败：限制自动重试，超限后记录失败并在参数配置页提示；
- Worker 重启：通过数据库租约恢复任务；
- API 调用 Worker 超时：返回稳定“语义服务不可用”错误；
- 当前模型文件被手工删除：启动校验发现后转为不可用和待重新下载；
- 修改门槛失败：保留原值并使用现有短暂错误提示。

- 重复增量任务合并；

### 15.2 数据库和 API 集成测试

- 384/1024 维向量写入；
- HNSW 余弦查询和门槛；
- 三种数据类型不串联结果；
- 模型未就绪时普通查询不受影响；
- 创建、修改、删除后的向量任务；
- 事件更名触发关联关系更新；
- 旧任务不能覆盖最新内容；
- 模型切换后旧向量被清除；
- 增强结果分页、去重和普通结果优先；
- Worker 不可用时返回稳定错误。

### 15.3 Worker 测试

- 下载进度；
- 固定文件清单和校验失败；
- 中断下载和重试；
- 服务重启后的租约恢复；
- 全量索引批处理；
- 单条失败不阻塞任务；
- 切换期间拒绝重复切换；
- 模型释放和重新加载。

常规自动化测试使用小型测试模型或模型适配器，不在每次 CI 中下载真实模型。另提供显式真实模型烟雾测试命令。

### 15.4 语义质量测试

固定测试集覆盖：

- 中英文同义事件；
- 不同措辞的具体案例；
- 原因和结果名称不同但语义相近的关系；
- 公司英文名、证券代码和中文描述混排；
- 容易错误关联的相似词。

验收要求：

- 明确相关记录能够进入前 10 条候选；
- 普通精确匹配始终排在语义新增结果之前；
- 默认中等门槛不会引入大量明显无关内容；
- 质量优先模型在固定测试集上不能明显弱于轻量模型。

### 15.5 性能测试

使用独立的约 10 万条业务记录数据集：

- Worker 下载或重建时，普通搜索不出现明显性能退化；
- 语义候选最多 100 条；
- 轻量模型热启动增强查询目标为 2 秒以内；
- 质量优先模型热启动增强查询目标为 5 秒以内；
- 冷启动模型加载时间单独记录；
- 全量索引持续显示进度，并能在 Worker 重启后恢复。

性能目标以开发环境实测记录为准，不把网络下载时间计入查询性能。
