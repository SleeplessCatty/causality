# P1-05 具体案例管理设计

版本：V1.0
日期：2026-07-21
状态：已完成
所属路线图步骤：P1-05 具体因果案例管理
前置步骤：P1-04 已完成人工验收并提交

## 1. 目标

完成具体案例的独立列表、传统搜索、创建、查看和编辑闭环，并允许一条具体案例同时支持多条抽象因果关系。

具体案例是一条确切发生过的真实事件简短叙述。它不是抽象事件，不作为因果图节点，也不在自身内部拆分具体原因和具体结果。关系与案例之间使用多对多关联。

P1-05 同时把 P1-04 的案例数量占位替换为真实统计，并在关系创建和编辑表单中提供案例搜索、复用、新建和解除关联功能。

## 2. 已确认规则

- 顶部增加独立的“具体案例”业务模块；
- 案例可以独立创建并保持未关联状态；
- 案例只有一项业务内容：真实事件的简短叙述；
- 内容去除首尾空白后为 1–50 字；
- 不单独保存结构化时间、地点、来源、说明或附件；相关信息由用户写入 50 字叙述；
- 去除首尾空白后，全库不允许内容完全相同的案例；
- 同一案例可以关联多条因果关系；
- 同一关系不能重复关联同一案例；
- 关系创建和编辑时案例可为空，也可以关联多条；
- 关系表单可以搜索并选择已有案例；
- 没有合适候选时，用户必须显式选择“创建新案例：当前内容”；
- 从关系表单移除案例只解除当前关联，不删除独立案例；
- 关系详情按关联时间倒序显示最近 5 条案例；
- 关系案例数实时统计，不写入关系表；
- 新增、编辑或解除案例关联不自动改变人工置信度；
- 不提供案例删除或合并。

## 3. 对既有模型的调整

P1-02 建立的旧模型把一条具体因果案例直接绑定到一条关系，并保存具体原因、具体结果、两个发生时间、说明和来源。该结构被本设计取代。

P1-05 采用：

```text
具体案例  ← 多对多关联 →  抽象因果关系
```

当前旧结构案例尚未开放业务管理，数据库中的案例均为固定或模拟测试数据。P1-05 迁移清理旧案例数据并重建新模型；抽象事件、事件别名和抽象因果关系不受影响。

不采用以下方案：

- 不继续把案例直属一条关系，否则无法先独立创建或被多条关系复用；
- 不把案例 ID 数组保存到关系 JSON 字段，否则无法可靠约束引用、统计和反向查询；
- 不使用先保存关系、再逐条调用关联接口的非原子流程，避免出现部分保存状态。

## 4. 阶段边界

P1-05 不实现：

- 案例删除、归档、恢复或合并；
- 结构化发生时间、时间范围、地点、来源和其他元数据；
- 反例、不确定案例、案例置信度、权重或审核状态；
- 根据案例数量自动调整关系置信度；
- 附件、批量导入和批量操作；
- AI、语义搜索或向量搜索；
- 局部因果图查询和展示；
- 移动端适配。

## 5. 全局界面约定

继续复用 P1-03 建立的全局应用壳和视觉系统。P1-05 不重新选择页面风格，不引入 UI 库、表单库或全局状态库。

顶部导航调整为：

```text
事件 | 因果关系 | 具体案例 | 系统状态
```

事件、关系和案例保持独立业务模块，通过应用内链接互相跳转。

## 6. 页面与路由

```text
/cases                         案例列表和搜索
/cases/new                     创建独立案例
/cases/:caseId                 案例详情
/cases/:caseId/edit            编辑案例
/relations                     关系列表和展开详情
/relations/new                 创建关系并选择案例
/relations/:relationId/edit    编辑关系及案例关联
```

### 6.1 案例列表

列表列为：

```text
案例内容 | 关联关系数 | 更新时间 | 操作
```

- Web 每页固定 30 条，API 支持 1–100 条；
- 默认按 `updated_at desc, id desc` 排序；
- 一个传统搜索框，只匹配案例内容；
- 支持通过 `relationId` 只查看某条关系关联的案例；
- 搜索词和关系筛选写入 URL；
- 使用服务端游标分页，不返回总数量；
- 操作列提供“查看”和“编辑”；
- 不提供删除入口；
- 加载、空数据、无搜索结果和失败状态沿用现有模块。

### 6.2 案例详情

详情页显示：

- 完整案例内容；
- 关联关系数量；
- 创建时间和最后更新时间；
- 当前关联的全部因果关系。

关联关系每页显示 30 条，按关联时间倒序。每条显示 `原因事件 → 结果事件`，并链接到关系列表的展开位置。

案例详情不提供关联编辑。关联的新增和解除统一在关系创建或编辑页面完成。

### 6.3 案例创建和编辑

表单只有“案例内容”一个业务字段：

- 单行或紧凑多行输入；
- 实时显示 0–50 字计数；
- 保存前去除首尾空白；
- 空内容或超过 50 字时阻止保存；
- 重复时拒绝保存，并提供已有案例查看入口；
- 编辑页面显示当前关联关系数，并提示修改会同步反映到所有引用位置；
- 编辑后若与另一案例重复，不自动合并。

创建成功进入案例详情；编辑成功返回案例详情。保存失败时保留输入，保存期间禁用重复提交。

### 6.4 关系表单中的案例区域

在现有关系字段下方增加“具体案例”区域：

```text
具体案例
  [案例搜索或新内容] [移除]
  [案例搜索或新内容] [移除]
  [+ 添加案例]
```

- 点击“添加案例”增加一行；
- 输入停止 250ms 后搜索候选；
- 候选最多 10 条，只显示案例内容；
- 选择候选后该行绑定已有案例 ID；
- 没有合适候选时显示“创建新案例：当前内容”；
- 只有用户点击该选项后，该行才成为待创建案例；
- 已选择行允许移除；
- 同一表单不能重复选择或创建相同内容；
- 案例区域可以为空；
- 编辑关系时预加载当前全部案例关联；
- 移除已有行只表示解除当前关系关联。

关系保存失败时保留事件、置信度、说明和全部案例行。

### 6.5 关系列表与展开详情

- 关系列表中的 `caseCount` 改为真实关联数量；
- 展开详情显示案例总数和最近关联的 5 条；
- 最近案例按关联表的 `linked_at desc` 排序；
- 超过 5 条时其余案例默认不读取、不展示；
- “查看全部案例”进入 `/cases?relationId=<id>`；
- 每条案例内容链接到案例详情；
- 关系置信度继续只由用户人工修改。

## 7. REST API

### 7.1 案例接口

| 方法 | 路径 | 用途 | 成功状态 |
|---|---|---|---:|
| `GET` | `/api/cases` | 列表、搜索、关系筛选和游标分页 | 200 |
| `GET` | `/api/cases/candidates` | 关系表单候选搜索 | 200 |
| `GET` | `/api/cases/:caseId` | 案例详情 | 200 |
| `GET` | `/api/cases/:caseId/relations` | 案例关联关系列表 | 200 |
| `POST` | `/api/cases` | 创建独立案例 | 201 |
| `PUT` | `/api/cases/:caseId` | 完整更新案例 | 200 |

不提供 `DELETE`。

案例表单请求：

```json
{
  "content": "2025年4月美国宣布新一轮关税措施"
}
```

案例列表项包含 ID、内容、关联关系数和更新时间。案例详情额外返回创建时间。候选项只包含 ID 和内容，不返回匹配原因或分数。

### 7.2 关系接口调整

关系列表响应中的 `caseCount` 从固定 `0` 改为非负整数。关系详情额外返回最近 5 条案例引用和真实案例总数。

关系创建和完整更新请求增加 `caseSelections`：

```json
{
  "causeEventId": "uuid",
  "effectEventId": "uuid",
  "confidence": 75,
  "description": null,
  "caseSelections": [
    { "type": "existing", "caseId": "uuid" },
    { "type": "new", "content": "2025年4月美国宣布新一轮关税措施" }
  ]
}
```

`caseSelections` 可以为空。`PUT` 使用该数组完整替换当前关系关联集合；案例实体本身不会因为不再出现在数组中而被删除。

## 8. 保存事务与并发规则

创建或编辑关系在一个短事务中完成：

1. 校验关系字段和案例选择；
2. 创建或更新关系；
3. 创建标记为 `new` 的案例；
4. 建立新增关联；
5. 删除已从编辑表单移除的关联；
6. 返回包含真实案例数的关系详情。

任一步骤失败时全部回滚，不产生孤立的新案例或部分关联。

API 保存时必须重新检查案例内容唯一性和关系内重复项，不能依赖前端候选搜索。若待创建内容已由其他请求写入，返回重复冲突和已有案例 ID，由用户改为选择已有案例。

独立编辑案例只更新案例内容和 `updated_at`；关联表不变，所有关系读取时立即显示新内容。

## 9. 数据库与迁移

### 9.1 `concrete_cases`

| 字段 | PostgreSQL 类型 | 空值 | 规则 |
|---|---|---|---|
| `id` | `uuid` | 否 | 主键，默认 `gen_random_uuid()` |
| `content` | `varchar(50)` | 否 | 规范化后的案例内容 |
| `created_at` | `timestamptz` | 否 | 默认当前时间 |
| `updated_at` | `timestamptz` | 否 | 默认当前时间，写操作显式更新 |

约束和索引：

- `content = btrim(content)`；
- `char_length(content)` 必须为 1–50；
- `content` 唯一；
- `lower(content)` 建立 trigram 搜索索引；
- `(updated_at desc, id desc)` 建立列表游标索引。

内容唯一性按去除首尾空白后的实际字符串判断，不合并不同大小写或不同内部空白的文本。

### 9.2 `causal_relation_cases`

| 字段 | PostgreSQL 类型 | 空值 | 规则 |
|---|---|---|---|
| `causal_relation_id` | `uuid` | 否 | 外键指向抽象因果关系 |
| `concrete_case_id` | `uuid` | 否 | 外键指向独立案例 |
| `linked_at` | `timestamptz` | 否 | 默认当前时间 |

约束和索引：

- `(causal_relation_id, concrete_case_id)` 联合主键；
- 两个外键均使用 `ON DELETE RESTRICT`；
- `(causal_relation_id, linked_at desc, concrete_case_id)` 支持计数和最近案例；
- `(concrete_case_id, linked_at desc, causal_relation_id)` 支持案例详情查询关系。

### 9.3 迁移与测试数据

P1-05 数据库迁移：

1. 删除旧 `concrete_causal_cases` 测试数据和旧表；
2. 创建 `concrete_cases`；
3. 创建 `causal_relation_cases`；
4. 更新 Drizzle Schema、迁移快照和完整性检查；
5. 更新固定种子与模拟数据生成器。

固定和模拟数据按新模型重新生成。模拟数据必须同时包含未关联案例、只关联一条关系的案例和被多条关系复用的案例，并保持给定 seed 下结果稳定。

`db:verify` 增加独立案例数、关系案例关联数、无效外键和重复关联检查。现有抽象事件、别名和关系计数保持不变。

## 10. 查询与性能

- 案例列表和候选搜索使用参数化 SQL；
- 列表游标绑定规范化搜索词和可选 `relationId`，拒绝跨查询复用；
- 关系列表使用集合聚合读取案例数量，禁止逐行查询；
- 关系详情只查询最近 5 条案例；
- 案例详情中的关系使用每页 30 条的游标分页；
- 关系编辑预加载该关系的全部案例引用，以支持完整替换；
- 不引入独立搜索服务、缓存服务或后台任务。

## 11. 错误处理

| HTTP | code | 场景 |
|---:|---|---|
| 400 | `VALIDATION_ERROR` | 内容、游标、筛选或案例选择不合法 |
| 400 | `CASE_SELECTION_DUPLICATE` | 同一关系请求中出现重复案例 |
| 404 | `CASE_NOT_FOUND` | 案例不存在 |
| 404 | `RELATION_NOT_FOUND` | 关系不存在 |
| 409 | `CASE_CONTENT_CONFLICT` | 案例内容已存在 |
| 500 | `INTERNAL_ERROR` | 未分类服务端错误 |

`CASE_CONTENT_CONFLICT` 返回已有案例 ID，供页面提供查看或改选入口。错误响应不返回 SQL、约束名称、堆栈或连接信息。

## 15. 审核结论入口

请重点审核：

1. 案例是最多 50 字的独立真实事件叙述，不再拆分具体原因和具体结果；
2. 不保存结构化时间、地点、来源或说明；
3. 案例与关系采用多对多关联；
4. 关系表单可以选择已有案例或显式创建新案例；
5. 关系展开只显示最近关联的 5 条案例；
6. P1-05 不提供删除、合并或自动置信度。
