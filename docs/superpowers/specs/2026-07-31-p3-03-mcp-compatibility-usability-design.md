# P3-03 MCP 兼容性与使用体验完善设计

日期：2026-07-31

状态：实施完成，等待人工复核

前置阶段：P3-01、P3-01R1 与 P3-02 均已完成

## 1. 目标

P3-03 在不增加因果知识业务能力的前提下，提高现有 MCP Server 的协议一致性、跨客户端可用性、故障可诊断性和使用文档完整性。

本阶段以 MCP 标准协议为兼容基础，以 Codex CLI/Desktop 为主要人工验收客户端。Streamable HTTP 是正式使用的默认入口，stdio 保留为开发、调试和兼容入口。客户端只要支持 MCP Tool，就应能够完成全部关键业务流程；Prompt、Resource、Skill 和斜杠命令只作为便捷入口。

## 2. 已确认原则

1. 采用“协议优先、Codex 重点验收”，不增加 Codex 专用服务端业务分支。
2. Streamable HTTP 是默认接入方式；stdio 是可选兼容和调试入口。
3. Tool 是通用能力基线。Prompt、Resource、Skill 和 `/` 命令不是 MCP 通用能力的必要前提。
4. 不修改 Web 页面；连接诊断通过命令行和自动化测试完成。
5. 所有 Tool 业务失败使用统一的结构化错误，同时保留普通语言错误说明。
6. 增加 `pnpm mcp:check`，以真实客户端身份执行只读黑盒诊断。
7. 容量基准使用 10,000 个原子事件、约 30,000 条因果关系和约 100,000 条具体案例及关联。
8. 正式维护 Codex、通用 Streamable HTTP、通用 stdio、MCP Inspector，以及 Docker Compose 和本地开发配置。
9. 为采集入库、事件分析、路径追踪、因果链审查和结果推测提供五条完整工作流示例。
10. MCP 调用日志采用结构化、脱敏格式，只写标准输出。
11. Streamable HTTP 支持多个并行客户端和会话；业务状态不依赖网络会话。
12. 现有 15 个 Tool、5 个 Prompt、4 个 Resource 严格保持向后兼容。
13. 本阶段不增加新的业务 Tool、Prompt 或 Resource。
14. 不恢复已经取消的跨模型采集质量测试集。

## 3. 非目标

P3-03 不包含：

- 新的因果知识查询、采集、分析或推测能力；
- Web 页面或移动端调整；
- 客户端专用服务端分支；
- Claude、Cursor 等客户端的逐一认证和界面截图；
- 应用内在线 AI、自动联网或网页采集；
- 新的数据库业务表或长期诊断历史；
- 记录完整请求、响应、对话或业务正文；
- 通过诊断命令修改正式知识、生成入库方案或轮换令牌；
- 语义模型下载、索引性能和检索质量重做；
- 因果图体验或性能优化；
- 破坏现有 MCP 接口的 V2 改版。

## 4. 当前能力基线

P3-03 开始时，MCP Server 已提供：

- 15 个 Tool：10 个只读知识与证据工具、5 个受控采集入库工具；
- 5 个 Prompt：采集入库、事件分析、路径追踪、因果链审查和结果推测；
- 4 个 Resource：领域规则、采集规则、能力清单和实时系统状态；
- Streamable HTTP 与 stdio 两种传输方式；
- 5 个同源 Markdown Prompt 和 5 个 Codex Skill；
- Bearer Token、不可变入库方案、事务提交、幂等和成功历史。

P3-03 只完善这些能力的公共质量，不改变它们的业务边界。

## 5. 方案选择

### 5.1 采用方案

采用“共享兼容内核 + 黑盒验收工具”：

- 在现有 MCP Server 内建立共享能力目录、统一错误转换和统一调用日志边界；
- HTTP 与 stdio 继续使用同一个 Server 工厂和能力注册流程；
- 在服务端外增加 `mcp:check`、协议兼容测试和容量基准；
- 通过真实协议连接验证行为，不只测试内部函数；
- 不增加新的代理服务、端口或客户端适配层。

### 5.2 未采用方案

不采用“只做外部测试”的方案，因为它会继续保留错误映射、日志和能力预期的分散定义。

不采用独立兼容代理，因为它会增加部署组件和故障点，并与协议优先原则冲突。

## 6. 总体架构

### 6.1 共享能力目录

建立单一内部能力目录，声明预期 Tool、Prompt 和 Resource 的稳定名称、类型及数量。目录供以下消费者复用：

- MCP Server 注册流程；
- HTTP 与 stdio 一致性测试；
- `pnpm mcp:check`；
- 协议兼容测试；
- 文档清单校验。

能力目录不是新的公开 Resource，不复制完整业务 Schema。具体 Tool Schema、Prompt 内容和 Resource 内容仍由现有注册模块生成。

目录必须检查名称唯一性。测试不得只断言总数，还要断言稳定名称集合。

### 6.2 双传输同源注册

Streamable HTTP 和 stdio 必须调用相同的 MCP Server 工厂。传输层只能处理连接、认证、会话和消息收发，不能分别维护业务能力。

两种传输必须公开相同的：

- Tool 名称、描述和输入 Schema；
- Prompt 名称、描述、参数和正文；
- Resource URI、名称、描述和内容；
- Server instructions；
- Tool 成功与业务错误结构。

HTTP 的 Bearer Token、会话 ID 和 HTTP 状态不适用于 stdio，这些传输固有差异不视为能力不一致。

### 6.3 兼容边界

现有公开接口遵守以下规则：

- 不重命名或删除公开能力；
- 不改变现有必填参数的语义；
- 新输入字段只能是可选字段，省略时保持当前行为；
- 新输出字段只能是兼容性扩展；
- 成功响应不增加破坏现有解析的统一外层包装；
- 明显偏离已批准设计的错误行为可以修复，但必须增加回归测试；
- 未来若需要破坏性变化，必须另行设计版本化接口。

## 7. Tool 描述规范

15 个 Tool 的描述和 Schema 文案按统一模板补齐：

1. 用途和适用场景；
2. 只读或受控写入属性；
3. 必要前置条件；
4. 分页、查询深度、数量和时间限制；
5. 是否需要用户明确确认；
6. 主要失败类别；
7. 成功后通常应调用的下一工具；
8. 不允许的用途。

描述用于帮助不同 AI 模型正确选择工具，但不得把 Prompt 中的大段业务规则复制到每个 Tool。稳定业务规则继续由同源 Prompt、Resource 和 Server instructions 提供。

## 8. 统一结构化错误

### 8.1 Tool 业务错误结构

Tool 业务失败必须设置 MCP `isError = true`，并同时返回简洁文本和以下结构化内容：

```json
{
  "error": {
    "code": "STABLE_ERROR_CODE",
    "category": "validation",
    "message": "面向用户的简洁说明",
    "retryable": false,
    "suggestedAction": "修改输入后重新调用",
    "details": {}
  }
}
```

固定类别为：

| 类别 | 含义 | 默认重试判断 |
| --- | --- | --- |
| `validation` | 输入字段、引用或业务格式无效 | 修改输入前不可重试 |
| `not_found` | 目标记录、方案或结果不存在 | 核对目标后再调用 |
| `conflict` | 唯一冲突、重复提交或互斥状态 | 重新查询或修改方案 |
| `stale_state` | 对比、方案或依赖状态已变化 | 重新对比或生成方案 |
| `unavailable` | API、数据库或语义服务暂不可用 | 服务恢复后可重试 |
| `internal` | 未预期系统错误 | 默认不可盲目重试 |

`retryable` 必须根据具体错误映射，不能只由类别机械决定。

`suggestedAction` 使用明确动作，例如重新查询候选、修改输入、重新生成方案、等待服务恢复或提示用户人工处理。

`details` 只允许包含安全 ID、字段路径、数量、状态和上限。禁止包含 Token、堆栈、SQL、数据库凭据、完整原子事件、完整具体案例、完整关系说明或对话内容。

### 8.2 文本兼容

部分客户端只展示 `content` 文本，因此结构化错误必须同时提供一段自包含的普通语言说明。文本至少包含错误含义和建议动作，但不要求客户端解析文本取得稳定代码。

### 8.3 协议和认证错误

以下错误保持在协议或 HTTP 层，不包装成 Tool 业务错误：

- Bearer Token 缺失或无效；
- initialize 消息无效；
- 协议消息结构无效；
- 会话 ID 无效或已经终止；
- Tool、Prompt 或 Resource 名称不存在。

这些错误使用 MCP SDK 和 HTTP 语义。协议测试固定验证状态、错误类型和不泄露内部信息，不固定依赖 SDK 的完整文案。

## 9. Streamable HTTP 会话

### 9.1 多会话

- 允许多个本机客户端并行初始化和调用；
- 每个会话独立维护传输状态；
- 错误会话不得终止或污染其他会话；
- 断线后客户端可以建立新会话；
- 服务端不保存跨会话对话上下文。

### 9.2 业务状态

入库方案、提交结果和成功历史保存在数据库中，不依赖网络会话。客户端断线后，可以在新会话中根据已有方案 ID 或结果 ID 继续查询。

同一方案的并发提交继续遵守现有不可变方案、状态机、事务和幂等规则。P3-03 不放宽写入权限。

### 9.3 令牌轮换

令牌轮换后：

- 旧令牌发起的后续 HTTP 请求必须失败；
- 新令牌可以建立新会话；
- 客户端收到认证失败后应提示重新复制配置；
- 不承诺保持旧网络连接可继续工作；
- 轮换操作和 Token 值不得出现在 MCP 调用日志中。

## 10. 结构化脱敏日志

### 10.1 日志边界

在 MCP 操作边界增加统一日志，而不是在 15 个 Tool 中分别实现。每次调用至少输出开始和完成事件；初始化、目录读取、Prompt、Resource 和 Tool 调用使用统一字段。

完成日志包含：

- requestId；
- transport；
- operation 或 toolName；
- clientName 和 clientVersion（客户端提供时）；
- durationMs；
- outcome：`success | business_error | protocol_error | system_error`；
- errorCode 和 retryable（存在错误时）；
- 安全的输入、输出数量摘要。

### 10.2 脱敏要求

所有级别禁止记录：

- Authorization 和 Bearer Token；
- 完整请求或响应正文；
- 完整对话；
- 完整事件、案例和关系文本；
- 数据库连接凭据；
- 未脱敏堆栈。

`debug` 级别可以增加字段路径、分页参数、深度、数量上限、状态和内部阶段名。系统异常堆栈只允许进入现有受控开发日志通道，并且必须先经过敏感信息检查。

日志输出到标准输出，由本机或 Docker 管理。P3-03 不建立数据库日志表、日志查询 API 或 Web 日志页面。

## 11. `pnpm mcp:check`

### 11.1 定位

`mcp:check` 是真实协议边界的只读诊断，不是内部单元测试，也不是新的 MCP Tool。

默认检查 Streamable HTTP；显式选择后检查 stdio。支持普通文本和 `--json` 输出。

### 11.2 配置与安全

HTTP 地址读取顺序：

1. 诊断专用环境变量；
2. 受控的项目本地配置；
3. 默认 `http://127.0.0.1:8081/mcp`。

Token 只能从环境变量或受控本地配置读取，不支持 `--token` 参数。错误输出不得回显 Token 或完整 Authorization 请求头。

stdio 模式启动独立 MCP 子进程，沿用现有 stdio 启动配置。子进程必须在成功、失败、超时或中断时被清理。

### 11.3 检查步骤

1. 检查地址或子进程是否可用；
2. HTTP 模式验证无 Token 请求被拒绝；
3. 使用有效配置完成 initialize；
4. 列出 Tool、Prompt 和 Resource；
5. 与共享能力目录比较名称、数量和重复项；
6. 读取一个代表性 Prompt；
7. 读取一个代表性 Resource；
8. 调用一个无副作用的普通搜索；
9. 使用无效只读参数触发预期业务错误并检查错误结构；
10. 正常终止客户端会话和相关资源。

诊断不得调用 `prepare_knowledge_changes` 或 `commit_knowledge_changes`，不得生成入库方案、修改知识数据、轮换令牌、下载模型或触发重新索引。

### 11.4 输出和退出码

文本输出逐项显示：

- 通过；
- 失败；
- 跳过；
- 耗时；
- 失败原因；
- 建议操作。

全部必需项通过时退出码为 `0`；任一必需项失败时为 `1`。可选项跳过不导致失败，但必须说明原因。JSON 输出使用稳定 Schema，供自动化环境消费。

## 12. 协议兼容测试

### 12.1 能力目录单元测试

- 15 个 Tool、5 个 Prompt、4 个 Resource 名称唯一；
- 目录集合与实际注册集合一致；
- HTTP 与 stdio 复用相同注册入口；
- 描述包含规定的用途、读写属性、前置条件和上限；
- 便携 Prompt 和 MCP Prompt 继续保持同源一致性。

### 12.2 协议集成测试

通过真实 MCP 客户端连接测试：

- initialize 和能力协商；
- Tool、Prompt、Resource 列举和读取；
- 缺失 Token、错误 Token 和合法 Token；
- 无效 Schema、未知能力和结构化业务错误；
- 成功响应向后兼容；
- Server instructions 可用；
- HTTP 与 stdio 公开能力一致。

测试对稳定字段做精确断言，对由 MCP SDK 控制的可变错误文案只断言语义和不泄露信息。

### 12.3 会话和并发测试

- 多个 HTTP 会话并行查询；
- 一个错误会话不影响其他会话；
- 断线后重新初始化；
- 错误会话 ID；
- 令牌轮换后旧 Token 失败、新 Token 成功；
- 同一入库方案的并发提交保持现有幂等与事务规则。

### 12.4 黑盒与生产测试

- `pnpm mcp:check` 分别检查 HTTP 和 stdio；
- 生产 Compose 冒烟测试验证 MCP 认证、能力目录和只读调用；
- 失败测试必须清理 MCP 子进程、会话、测试数据库和 Compose 资源；
- Codex CLI/Desktop 继续作为人工验收，不把客户端 UI 自动化纳入仓库测试。

## 13. 代表性容量基准

### 13.1 数据集

新增 `pnpm mcp:benchmark`，在隔离数据库中使用固定随机种子生成：

- 10,000 个原子事件；
- 约 30,000 条有向因果关系；
- 约 100,000 条具体案例及关联；
- 一组最多 50 个原子事件及其关系、案例候选。

数据生成必须分批写入，不把全部记录同时保存在内存。基准结束后必须清理隔离数据库和临时文件。

### 13.2 覆盖场景

- 普通事件、案例和关系搜索；
- 所有页面的游标或页码续取；
- 事件、案例和关系详情；
- 20、50、100 个原子事件的局部图；
- 最大合法深度的因果路径；
- 多段证据包；
- 最多 50 个原子事件候选的库内对比；
- 入库方案生成但不提交；
- 多个并发只读 HTTP 会话。

语义模型下载、索引生成和增强搜索质量不进入每次 MCP 基准，继续由 P2-02 专项能力负责。

### 13.3 指标

每个场景记录：

- 冷启动耗时；
- 重复运行耗时；
- 响应字节数；
- 返回记录数量；
- 截断状态；
- MCP 进程内存峰值；
- 成功和失败数量。

第一版只建立基线，不把首次耗时直接设为发布阻断阈值。以下正确性条件立即成为门禁：

- 不崩溃或无限等待；
- 分页不遗漏、不重复；
- 数量和截断标记正确；
- 响应有界；
- 路径扩展遵守上限；
- 请求结束后内存可以回收；
- 诊断和基准不修改正式业务数据库。

基准只提交简洁汇总，不提交生成数据库、完整响应或大体积日志。

### 14.3 五条工作流手册

1. 会话采集与确认入库；

4. 用户因果链审查；
5. 基于知识库的后续结果推测。

每条流程包含普通语言启动语句、MCP Prompt、Codex Skill、预期 Tool 顺序、用户确认点、正常输出轮廓、常见失败和恢复步骤。

所有示例使用稳定的测试数据，不依赖联网。AI 与 Tool 使用 JSON，AI 对用户输出普通语言，CSV 只用于文件导入导出。

## 15. 实施任务顺序

### Task 1：共享能力目录与双传输一致性

建立内部能力目录和一致性测试，不改变公开能力。
