# 数据维护问题行内处理设计

日期：2026-07-27  
状态：待用户审核  
适用阶段：P2-03 数据治理问题处理界面调整

## 1. 目标

将数据维护问题从独立弹窗和编辑页返回流程，调整为与因果关系列表一致的行内展开处理：

- 列表直接显示严重程度、问题类型、问题来源和处理入口；
- 问题来源使用可读名称和详情链接，不在主界面展示内部 ID；
- 同一时间只展开一条问题；
- 展开面板只显示问题描述、处理建议和当前问题真正支持的处理方案；
- 有完整自动处理方案时，用户选择或确认方案后执行；
- 只能人工修改的问题不提供自动处理按钮；
- 数据修改和问题状态更新必须处于同一事务；
- 取消编辑页返回定位和单问题重新检查，人工修改后只通过完整数据检查重新判断。

本设计替代 P2-03 Task 12 中的独立问题弹窗、`open_edit` 动作、编辑页返回标记和单问题重新检查交互。检查任务、孤立数据统计、问题筛选和每页 50 条保持不变。

## 2. 不包含

- 不增加批量处理或一键处理全部问题；
- 不保存处理操作审计历史；
- 不增加永久忽略规则；
- 不改变完整数据检查的按需手动执行方式；
- 不自动判断事件的原子性或因果关系的真实性；
- 不为人工修改类问题直接修改业务字段；
- 不为移动端重新设计布局。

## 3. 已确认交互原则

### 3.1 列表结构

问题列表固定为四列：

1. **严重程度**：错误或警告；
2. **问题类型**：显示面向用户的中文类型名称；
3. **问题来源**：显示相关原子事件、具体案例、因果关系、别名或关键词；
4. **处理入口**：未处理问题显示“展开/收起”，已处理问题显示静态“已处理”。

问题描述和处理建议不再占用列表列，统一放入展开面板。

### 3.2 展开行为

- 使用与因果关系列表相同的 `expanded=<issueId>` URL 状态；
- 同一时间只允许展开一条；
- 展开下一条时自动收起上一条；
- 切换页码或筛选条件时清除展开项；
- “展开/收起”使用替换当前历史记录的方式更新 URL；
- 不保留独立弹窗，不提供关闭按钮；
- 点击来源链接使用正常站内导航；不增加数据维护专用返回状态；
- 不要求从详情页或编辑页返回后重新定位原问题。

### 3.3 展开面板

所有面板固定包含：

- **问题描述**：说明检测到了什么；
- **处理建议**：说明用户应该如何判断或处理。

按问题能力可增加：

- **处理方案**：系统能够完整、安全执行的数据操作；
- **确认处理**：只在存在可执行方案时显示；
- **忽略此问题**：所有未处理问题均可使用。

不再显示：

- 关闭按钮；
- 单独的问题来源详情区；
- 与处理建议重复的“处理方式”区；
- 跳转编辑页面按钮；
- 单问题重新检查按钮。

按钮顺序固定为：

```text
确认处理    忽略此问题
```

比较与合并类默认不选中任何方向。选择方向后显示该方向的实时影响并启用“确认处理”。只有一个固定方案的清理、删除和时间修复类，确认按钮默认可用。

### 3.4 处理完成

- 自动处理成功后，问题状态改为已处理并自动收起；
- 当前筛选为“未处理”时，该行立即移出当前列表；
- 当前筛选为“全部”或“已处理”时，该行保留，处理入口显示静态“已处理”；
- 已处理问题不再展开；
- 忽略只处理当前检查快照中的问题；
- 下次完整检查时，如果实际问题仍存在，将重新生成未处理问题。

## 4. 问题来源展示

### 4.1 通用规则

- 来源名称均使用现有 `OverflowText` 规则；
- 主列表超长内容单行省略；
- 所有可能被省略的来源均提供固定尺寸、内容可滚动的完整提示；
- 原子事件名称链接到事件详情；
- 具体案例内容链接到案例详情；
- 因果关系显示为“原因事件 → 结果事件”；
- 原因、结果事件名称分别链接到事件详情；
- 中间箭头只在关系详情能够安全加载时链接到关系详情；
- 别名和关键词显示“所属事件名称 · 别名/关键词文本”；
- 引用记录已不存在时显示“已不存在”，不伪造详情链接；
- 正常界面不显示 UUID；缺失引用通过可读状态说明。

### 4.2 列表接口

问题分页接口应一次返回当前页全部问题的可读来源，禁止前端为每一行单独请求来源。建议新增：

```ts
interface DataCheckIssueSourceItem {
  type: 'event' | 'case' | 'relation' | 'alias' | 'keyword' | 'missing';
  role: 'target' | 'related' | 'cause' | 'effect' | 'owner' | 'value';
  label: string;
  detailPath: string | null;
}

interface DataCheckIssueSource {
  displayKind: 'single' | 'pair' | 'relation' | 'owned_value' | 'broken_reference';
  items: DataCheckIssueSourceItem[];
  relationDetailPaths: string[];
  auxiliaryText: string | null;
}
```

`relationDetailPaths` 用于同方向重复关系等需要区分关系 A/B 的问题。列表仓储必须通过批量查询或关联查询组装当前页来源，避免 N+1 查询。

## 5. 五类展开面板

### 5.1 比较与合并

适用于事件、案例或关系的重复/相似问题。

- 展示两个来源记录；
- 提供两个保留方向；
- 默认不选中；
- 每个方向由服务器分别计算影响；
- 选择方向后显示关系迁移、关系删除、案例关联迁移、案例关联删除和主记录删除数量；
- 确认后执行所选方向；
- 用户也可以通过来源链接查看或人工修改数据，然后重新执行完整检查。

### 5.2 自动清理

适用于能够唯一确定删除对象或重排顺序的问题。

- 展示固定处理方案；
- 明确说明只清理目标从属数据或关联；
- 不提供方向选择；
- 确认按钮默认可用。

### 5.3 删除异常因果关系

适用于关系自环和事件引用失效。

- 展示固定删除方案；
- 展示将删除的因果关系数和案例关联数；
- 明确说明不会删除原子事件或具体案例；
- 使用危险操作视觉，但沿用应用现有按钮风格；
- 确认按钮默认可用。

### 5.4 自动修复时间

适用于 `updated_at < created_at`。

- 展示当前创建时间、异常更新时间和修复后更新时间；
- 修复规则为 `updated_at = greatest(updated_at, created_at)`；
- 明确说明不修改业务内容或关联；
- 确认按钮默认可用。

### 5.5 人工修改提示

适用于业务字段内容异常或超出范围。

- 只显示问题描述和处理建议；
- 来源名称或关系箭头是进入详情页的入口；
- 不显示处理方案；
- 不显示确认按钮；
- 只保留“忽略此问题”；
- 用户修改数据后，通过页面顶部“检查数据”重新执行完整检查。

## 7. 后台自动处理完整性

### 7.1 自动方案准入原则

只有满足以下条件的问题才能返回自动处理方案：

1. 处理目标和处理范围可由服务器完整确定；
2. 处理动作有封闭的服务端白名单；
3. 提交时能够重新验证问题仍存在；
4. 所有受影响记录能够在稳定顺序下锁定；
5. 影响计算与实际执行使用相同规则；
6. 数据修改和问题状态更新可以在同一事务提交；
7. 失败时不会遗留部分修改。

任一条件不满足时，后端不得返回“确认处理”动作，只能返回人工处理提示或要求重新执行完整检查。

### 7.2 通用事务流程

所有 `merge`、`cleanup`、`delete_relation`、`repair_timestamp` 和 `ignore` 使用：

1. 开启 PostgreSQL `SERIALIZABLE` 事务；
2. 根据 `snapshotId + issueId` 锁定当前问题；
3. 验证问题仍为未处理且属于当前快照；
4. 重新执行该类型的确定性判定；
5. 加载并按稳定 ID 顺序锁定受影响业务记录；
6. 重新生成允许动作和实时影响；
7. 验证客户端提交的动作与服务器允许动作完全一致；
8. 执行数据修改；
9. 在同一事务中将当前问题标记为已处理；
10. 提交事务；
11. 提交后刷新问题列表和受影响业务缓存。

任何步骤失败：

- 回滚全部数据修改和问题状态；
- 返回稳定错误码和用户可读原因；
- 前端保留展开状态和已选择方案；
- 不把问题标记为已处理。

发生序列化冲突时允许服务器内部重试一次；再次失败后返回并发冲突，不继续执行旧方案。

读取处理上下文的 GET 请求必须是只读操作，不得因为目标缺失而自动修改问题状态。

### 7.3 事件合并

事件合并必须：

- 只允许当前问题中的两个事件互为保留/合并对象；
- 按 UUID 稳定顺序锁定两个事件；
- 合并别名和关键词，按标准化文本去重；
- 保留原有稳定顺序，关键词重新编号；
- 合并后别名或关键词超过 20 条时中止并回滚；
- 将被合并事件涉及的入边和出边重定向到保留事件；
- 重定向形成自环时删除该关系及其关系—案例关联；
- 重定向与现有同方向关系冲突时，合并案例关联并删除重复关系；
- 关系—案例关联使用唯一约束去重；
- 完成迁移后删除被合并事件；
- 返回所有受影响事件、关系和案例 ID。

### 7.4 具体案例合并

案例合并必须：

- 锁定两个案例；
- 将被合并案例的全部关系关联迁移到保留案例；
- 对已存在的相同关系—案例关联去重；
- 删除被合并案例；
- 不修改或删除因果关系；
- 返回受影响案例和关系 ID。

### 7.5 因果关系合并

关系合并必须：

- 锁定两条关系；
- 再次验证原因事件和结果事件均相同；
- 将被合并关系的案例关联迁移到保留关系；
- 对重复案例关联去重；
- 删除被合并关系；
- 不修改事件、置信度或关系说明；
- 返回受影响事件、案例和关系 ID。

### 7.6 自动清理

- 失效别名/关键词：只删除问题指定的从属记录；
- 失效关系—案例关联：使用关系 ID 与案例 ID 组成的完整键删除；
- 重复别名：再次验证与保留别名属于同一事件且标准化文本相同，只删除问题目标；
- 重复关键词：再次验证同事件、标准化文本相同，删除问题目标后重排位置；
- 关键词重排：锁定该事件全部关键词，拒绝超过 20 条或仍有重复标准化值的情况，再按 `position + id` 稳定顺序编号为 `1..n`。

### 7.7 删除异常关系

- 仅允许关系自环、原因事件引用失效和结果事件引用失效三种类型；
- 锁定目标关系并重新验证问题；
- 先删除该关系的全部关系—案例关联，再删除关系；
- 原因事件、结果事件和具体案例均保留；
- 实际删除数量与提交前影响不一致时中止并回滚。

### 7.8 修复时间

- 问题类型、目标类型和表名采用固定服务端映射；
- 不接受客户端表名或字段名；
- 只在 `updated_at < created_at` 时更新；
- 使用 `updated_at = greatest(updated_at, created_at)`；
- 影响行数必须恰好为 1，否则回滚；
- 不修改任何业务字段。

### 7.9 忽略

- 只锁定并更新当前快照中的当前问题；
- 不修改业务数据；
- 不创建永久例外；
- 下次完整检查仍按实际数据重新生成问题。

## 8. 统一状态与错误反馈

### 8.1 加载

- 展开后加载服务器处理上下文；
- 加载期间显示行内骨架；
- 不显示可点击的确认或忽略操作；
- 加载失败时在面板内显示原因和“重新加载”。

### 8.2 提交

- 提交过程中保留当前面板和已选方案；
- 禁止切换展开项、重复确认和忽略；
- 确认按钮显示“处理中…”；
- 页面其他普通导航不主动中断已提交请求。

### 8.3 失败

- 面板保持展开；
- 保留合并方向；
- 错误显示在面板操作区上方；
- 操作按钮重新启用；
- 用户可以再次确认或忽略；
- 数据/快照已变化时禁用旧方案，并提示使用顶部“检查数据”重新生成完整快照。

### 8.4 成功

- 只有事务提交成功后更新前端；
- 当前未处理筛选下移除该行；
- 全部/已处理筛选下改为静态“已处理”；
- 刷新检查汇总、问题分页、受影响列表/详情、候选项和因果图缓存；
- 不显示独立成功弹窗。

## 9. 接口调整

保留：

```text
GET  /api/data-checks/issues/:issueId/action-context?snapshotId=:snapshotId
POST /api/data-checks/issues/:issueId/actions
```

移除：

```text
POST /api/data-checks/issues/:issueId/recheck
```

动作集合调整为：

```ts
type DataCheckActionRequest =
  | { type: 'merge'; snapshotId: string; keepId: string; mergeId: string }
  | { type: 'cleanup'; snapshotId: string }
  | { type: 'delete_relation'; snapshotId: string }
  | { type: 'repair_timestamp'; snapshotId: string }
  | { type: 'ignore'; snapshotId: string };
```

删除 `open_edit` 动作和编辑路径。来源详情路径由问题列表/处理上下文的只读来源数据提供，不属于可执行动作。

面板类型调整为：

```ts
type DataCheckPanelKind =
  | 'merge'
  | 'cleanup'
  | 'delete_relation'
  | 'repair_timestamp'
  | 'manual';
```

## 10. 前端组件边界

建议组件：

- `DataCheckIssueTable`：筛选、分页和行渲染；
- `DataCheckIssueSource`：四种来源布局、链接和省略提示；
- `DataCheckExpandedRow`：加载上下文、统一状态和动作提交；
- `DataCheckIssueSummary`：问题描述与处理建议；
- `DataCheckActionPlan`：固定方案；
- `DataCheckMergePlan`：方向选择和方向影响；
- `DataCheckActionError`：加载、冲突和事务错误；
- `useDataCheckExpandedIssue`：`expanded` URL 状态；
- `useDataCheckIssueAction`：统一提交与缓存刷新。

不再保留：

- `DataCheckIssueDialog`；
- `DataCheckMergeDialog`；
- 数据维护专用编辑返回状态；
- `recheck` URL 标记和消费逻辑。

## 11. 测试要求

### 11.1 合同测试

- 26 种问题类型均映射到封闭面板类型；
- 自动动作拒绝未知字段和任意目标 ID；
- 合并只接受当前问题中的两个方向；
- 来源对象拒绝无效路径和不匹配的展示类型；
- 已处理问题不返回可执行动作；
- 不再接受 `open_edit` 和单问题 recheck 合同。

### 11.2 后端单元与集成测试

每一种自动处理问题至少覆盖：

- 上下文返回正确的来源、处理方案和影响；
- 问题已变化时不返回旧动作；
- 正常处理后数据与问题状态同时提交；
- 处理逻辑抛错时数据与问题状态同时回滚；
- 并发修改时拒绝旧方案；
- 忽略只影响当前快照。

额外覆盖：

- 事件合并的入边、出边、自环、同方向冲突、别名/关键词去重和上限；
- 案例合并的关联迁移与去重；
- 关系合并两个方向的关联迁移与去重；
- 所有清理类型的精确删除目标；
- 删除异常关系保留事件与案例；
- 三类时间修复；
- 来源批量查询无 N+1；
- 处理上下文 GET 不修改问题状态。

### 11.3 前端测试

- 四列表头与所有来源展示类型；
- 来源名称省略提示和详情链接；
- 同时只展开一条；
- 展开状态与因果关系列表保持一致；
- 页码/筛选改变时收起；
- 五类面板内容与按钮差异；
- 合并默认不选择、选择后显示对应影响并启用确认；
- 固定方案确认默认可用；
- 人工问题只有忽略；
- 提交中锁定；
- 失败保留展开状态与选项；
- 成功后的筛选行为；
- 已处理问题不可展开；
- 不再生成编辑返回状态或 recheck 请求。

## 12. 验收标准

- 用户无需打开弹窗即可理解和处理问题；
- 列表中不再显示内部 ID；
- 26 种问题都有明确来源展示和面板归属；
- 19 种自动处理问题均有完整、白名单化、事务化的后台处理；
- 7 种人工问题不会出现误导性的确认按钮；
- 自动处理失败不会产生部分数据修改或错误的已处理状态；
- 人工修改后无需返回定位，只需重新执行完整检查；
- 页面视觉与现有紧凑型桌面应用、因果关系列表和通用组件一致。
