# P3-01R1 Task 2 统一采集规范与 V2 Prompt 设计

日期：2026-07-29
状态：已完成
所属阶段：P3-01R1 MCP 查询完整性与采集质量优化

## 1. 目标

在不修改数据库结构、采集 JSON Schema、MCP 工具数量和入库事务流程的前提下，升级 `causality_capture` 的唯一规则源，使外部 AI 在调用候选对比前能够更稳定地完成以下工作：

- 围绕用户关心的会话主线提取知识；
- 根据当前讨论语境生成细粒度、精准且可作为因果端点的原子事件；
- 区分原子事件和真实发生的具体案例；
- 避免把间接因果链压缩成没有依据的直接关系；
- 严格按照 MCP 工具公开的 JSON Schema 组装完整候选集合；
- 在信息不足时保持保守：质量依据不足的内容直接省略；内容有效但无法判断新增或复用时使用 `skip`，不依靠臆想补齐数据。

本任务只增强 AI 侧规范与自检。服务端结构化质量门禁属于 Task 3，不在本任务提前实现。

## 2. 保持不变的产品边界

1. 只有用户明确发起采集与入库指令时才启动采集。
2. 采集范围仍根据当前可见会话中的最后一个成功标记自动确定。
3. 一次最多处理 50 条去重后的原子事件。
4. AI 内部使用 JSON 调用 MCP；CSV 只用于文件导入导出，不参与 AI 导入。
5. 现有事件名称、案例内容、关系端点和关系说明不可修改。
6. 复用原子事件时，只能追加别名、追加关键词或替换说明。
7. 置信度仍由案例关联变化触发应用自动计算，AI 不直接填写或修改。
8. 用户明确确认最新完整方案之前，不得调用正式入库工具。
9. 不增加跨模型采集质量测试集。

## 3. 唯一规则源和三个消费入口

### 3.1 唯一规则源

继续使用 `apps/mcp/src/prompts/capturePrompt.ts` 中的 Prompt 构建函数作为唯一可编辑规则源，并在正文中标记为 V2。

该模块只暴露两个稳定接口：

- 构建完整采集指令文本；
- 将同一文本注册为 `causality_capture` MCP Prompt。

不再新增另一份手写业务规则文档，也不让运行时从文件系统读取 Prompt。这样 HTTP 与 stdio 使用同一个实现，部署产物不依赖仓库文档路径。

### 3.2 MCP Prompt

MCP Prompt 名称继续使用 `causality_capture`，避免破坏已有客户端配置。客户端取得的正文必须与唯一规则源完全一致。

### 3.3 便携 Markdown Prompt

`prompts/causality-capture.md` 继续通过现有生成命令从唯一规则源覆盖生成，不允许人工维护。自动化测试继续要求两者逐字节一致。

### 3.4 示例 Skill

2. 其他完整支持 MCP Prompt 的客户端仍可直接调用标准 MCP Prompt；
3. 两者均不可用时停止并提示配置方式。

Skill 不复制原子事件定义、候选字段、判断规则或入库流程，避免形成第四份规则源。本任务不创建或安装用户全局 Skill。

## 4. V2 原子事件规则

原子事件是“在当前讨论语境和知识建模目的下，不再需要继续拆分、能够精准作为一条因果关系端点的最小事件表达”。原子性是相对当前问题判断的，不等同于完全抽象化。

### 4.1 允许的表达

- 可以包含真实主体，例如“阿里巴巴美股股价上升”“特斯拉汽车销量下滑”；
- 可以包含改变因果含义所必需的范围限定，例如“国内融资成本上升”；
- 使用“主体或范围 + 单一状态、动作或变化方向”表达；
- 名称应足以区分因果含义不同的事件，但不堆叠一次真实发生记录的时间、地点和过程细节；
- 说明字段只用于解释事件边界，不得借说明再加入第二个事件。

### 4.2 必须拆分的表达

一句话如果包含两个可以分别作为关系端点的变化，必须拆分。例如：

```text
美联储提高政策利率并导致美国企业融资成本上升
```

拆为：

```text
美联储政策利率上升
美国企业融资成本上升
```

再建立有依据的有向关系。名称中的“并且”“然后”“导致”“从而”等连接结构是复合事件提示，但 AI 必须按语义判断，不能只依靠关键词机械拆分。

### 4.3 不能错误合并的表达

判断新表达是否与已有事件相同时，必须同时比较：

- 主体；
- 地域或适用范围；
- 状态或动作；
- 变化方向；
- 对当前因果链有意义的粒度。

主体、范围或变化方向不同并导致因果含义变化时，不得为了复用而合并。例如“融资成本上升”与“国内融资成本上升”不必然是同一事件；只有当前语境明确两者边界一致时才可复用。

## 5. 主线相关性规则

AI 在生成候选前先在内部确定：

- 一个简短的主题锚点；
- 用户正在追溯原因、结果还是双向链路；
- 当前可见会话中能够支持主线的事实范围。

候选必须满足：

1. 原子事件位于主题锚点的原因链或结果链上；
2. 每个准备新增或复用的原子事件至少是一个有效候选关系的端点；
3. 每个具体案例至少支持一个有效候选关系；
4. 只提供背景说明、没有进入主线因果链的事件和案例不采集；
5. 无法判断是否属于主线时采用保守策略，不扩展无关知识。

## 6. 具体案例规则

具体案例是已经真实发生的一次事件记录，不是抽象规律、预测、假设或通用说明。

- 只使用当前可见会话已经提供或客户端已经核实的事实；
- 在 100 字限制内保留能够区分该次发生记录的主体、时间或时间范围，以及必要地点或结果；
- 不得编造缺失的日期、数字、地点、来源或时间间隔；
- 同一真实发生记录的不同措辞视为复用候选，不得在本批次重复创建；
- 判断是否为同一案例时综合比较主体、发生时间、动作和结果，无法可靠判断时选择 `skip`；
- 网页 URL、标题和引文仍不作为独立业务字段提交。

## 7. 直接与间接因果关系规则

因果关系必须有当前可见会话中的明确陈述、真实案例或清楚的机制说明作为依据。仅有时间先后、共同出现、相关性或常识上的可能性不足以建立关系。

### 7.1 中间事件

如果信息只支持：

```text
A → B → C
```

则只建立 `A → B` 和 `B → C`。只有存在独立依据证明 A 直接导致 C 时，才同时建立 `A → C`。

- 中间机制已经在会话事实中明确出现时，将其提取为原子事件；
- 只怀疑存在中间事件、但当前内容无法确认时，不得自行发明；
- 无法确认直接性的关系不得进入候选集合；只有关系内容本身有效、但无法判断新增或复用时，才在方案决策中使用 `skip`。

### 7.2 方向和自环

- 原因和结果方向必须与当前依据一致；
- 反向关系不能因为文字顺序被误判为正向；
- 原因和结果不得引用同一个原子事件；
- 已有反向关系不妨碍新增正向关系，但 AI 必须确认它们表达的是两个不同方向的事实。

## 8. 调用对比工具前的完整自检

AI 必须先在内部完成一次完整候选自检，再调用 `compare_knowledge_candidates`。自检按以下顺序执行：

1. **范围**：采集区间、主题锚点和追溯方向正确；
2. **相关性**：没有脱离主线的事件或案例；
3. **原子性**：每个事件只表达一个状态、动作或变化；
4. **真实性**：具体案例确实是当前内容中已经发生的事实；
5. **因果依据**：每条关系方向合理，不用时间先后或想象替代因果依据；
6. **直接性**：已提取当前内容明确给出的必要中间事件；
7. **批次去重**：事件、案例、同方向关系和案例关联在当前批次内各自唯一；
8. **引用完整**：关系端点引用本批次事件 `ref`，案例关联引用本批次关系和案例；
9. **无孤立候选**：有效事件进入至少一条有效关系，有效案例进入至少一条有效案例关联；
10. **数量和字段**：去重后事件不超过 50 条，所有字段符合 MCP 工具发布的 JSON Schema。

质量不合格且无法修复的内容不进入候选集合。内容本身有效、但无法判断应该新增还是复用时，才在方案决策中选择 `skip`。

## 9. 严格 JSON 调用规范

Prompt 不复制完整 JSON Schema，而是要求 AI 严格使用 MCP 工具实时发布的 Schema，避免文档和代码漂移。同时明确以下高频错误约束：

- 直接发送工具参数对象，不把 JSON 包装成 Markdown、字符串或 CSV；
- 一次提交包含四类完整候选数组，不拆成多次局部对比；
- 原子事件始终显式提供 `aliases` 和 `keywords` 数组，无内容时使用空数组；
- 可空说明没有可靠内容时使用 `null`，不编造占位文字；
- 使用批次内稳定、唯一且可读的 `ref`，推荐 `event-001`、`case-001`、`relation-001`；
- `ref` 不是数据库 ID，在同一次对比、方案生成和修改循环中不得无故变化；
- 关系只引用事件 `ref`，案例关联只引用关系 `ref` 和案例 `ref`；
- 对比结果必须原样随候选集合交给方案生成工具，不得伪造、删改或手工重算；
- 决策必须覆盖完整候选集合，依赖项被 `skip` 时其关系或案例关联同步 `skip`；
- 方案修改后重新提交一份完整候选、对比和决策集合，不提交差异补丁。

## 10. 复用与新增决策规范

### 10.1 原子事件

- 名称、别名和语义候选只是判断依据，不自动等于同一事件；
- 主体、范围、状态、方向和粒度一致时优先复用；
- 明确是不同事件时新增；
- 无法可靠区分时 `skip`；
- 复用时只能提出追加别名、追加关键词或替换说明；替换说明必须更准确地描述同一事件边界，不能改变已有事件含义。

### 10.2 具体案例

- 明确是同一次真实发生记录时复用；
- 明确是另一时间、主体或过程的发生记录时新增；
- 只有相似主题但无法确认同一发生记录时 `skip`。

### 10.3 因果关系和案例关联

- 相同原因端点、结果端点和方向的已有关系复用；
- 反向关系不是同一关系；
- 已有关联复用，不重复创建；
- 被跳过的事件、案例或关系不能被仍计划入库的下游决策引用。

## 11. 自动分类

从提取开始到首次完整方案生成，所有检查、库内对比和决策由 AI 自动完成，不在中途要求用户逐项判断。全部提取结果分为：

- **确信数据**：通过质量检查且可以可靠决定 `create` 或 `reuse`；用户确认方案后才实际提交；
- **存疑数据**：与主线相关且结构有效，但新增、复用或边界仍不能可靠判断；默认 `skip`，在方案中说明疑点和建议；
- **忽略数据**：与主线无关、依据不足、批次内重复或无法形成有效业务数据；不进入候选写入集合，但必须在当前会话的用户可读方案中说明内容和忽略原因。

服务端不可变方案继续只保存符合 MCP Schema 的候选和决策。忽略数据只用于当前会话的完整方案说明，不伪装为已保存记录。用户直接确认时只提交确信数据；存疑和忽略数据保持不入库。用户可以要求调整任一分类，AI 随后重新自检、完成必要对比并生成新的完整方案。

## 12. 用户可读方案与确认循环

首次完整方案之前仍自动执行提取、自检、对比和方案生成，不逐步打断用户。展示给用户的内容继续使用普通语言，并清楚列出：

- 主题和采集范围；
- 新增、复用和暂不入库的原子事件；
- 新增、复用和暂不入库的具体案例；
- 因果关系方向和案例关联；
- 原子事件补充内容及预期自动置信度变化。

用户提出修改后，AI 重新执行受影响候选的检查与必要对比，生成替代旧方案的最新完整方案。只有用户明确确认该最新方案后才允许提交。

首次方案应按“确信数据、存疑数据、忽略数据”分组，并在每组中按原子事件、具体案例、因果关系和案例关联展示可读内容、AI 决策和原因。展示后询问用户修改方案或明确确认最新方案。

## 13. 错误处理

- MCP Schema 解析失败时，根据字段路径修正完整参数对象后重试同一步骤；
- 数据错误根据 `affectedRefs`、`aiCanRepair` 和建议动作修正候选或决策，重新生成完整方案并再次等待确认；
- 系统或配置错误不通过改写业务数据规避，向用户说明需要人工处理或稍后重试；
- 不得在工具失败、响应不明或方案失效时宣称入库成功。

## 16. 人工复核

1. 从 MCP 客户端读取 `causality_capture`，确认显示 V2 规则且没有多份冲突说明；
2. 使用包含真实主体和范围限定的会话，确认不会被强制改写为完全抽象事件；
3. 使用包含复合事件的会话，确认方案会拆分为两个端点和一条关系；
4. 使用只支持 `A → B → C` 的会话，确认不会无依据生成 `A → C`；
5. 混入与主线无关的背景事件，确认其不会进入候选方案；
6. 提供相似但主体或范围不同的已有事件，确认 AI 不会仅因语义相似就强制复用；
7. 确认最终仍按“完整方案—用户修改—最新方案明确确认—事务入库”流程运行。
8. 确认首次方案前没有逐项提问，方案完整显示确信、存疑和忽略数据；直接确认时仅提交确信数据。
