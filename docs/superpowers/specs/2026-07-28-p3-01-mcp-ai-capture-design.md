# P3-01 MCP Server 与外部 AI 采集入库设计

## 1. 文档状态

- 阶段：P3-01
- 状态：设计已审核通过
- 日期：2026-07-28
- 目标：让外部 AI 客户端通过标准 MCP 查询 Causality、分析因果问题，并在用户审核后将当前会话中的知识安全写入现有数据库。

## 2. 目标

用户在外部 AI 客户端中围绕一个问题进行多轮对话。AI 可以使用客户端自身的联网搜索能力查找真实事件，并结合 Causality 中已有的原子事件、具体案例和因果关系继续追问、分析原因与结果。

用户明确发出采集指令后，AI 自动完成会话范围识别、知识提取、库内对比和第一版入库方案生成。用户只参与方案审核循环；只有用户明确确认最新完整方案后，系统才执行一次完整的事务入库。

本阶段不在 Causality 内配置在线大模型或联网搜索。Causality 只提供稳定的 MCP 能力、确定性业务校验、本地语义候选查询、事务写入和审计记录。

## 3. 核心原则

1. 数据库只保存原子事件、具体案例和因果关系三类业务数据，以及它们已有的关联。
2. 网页 URL、网页标题、完整会话、搜索过程和 AI 推理不进入业务数据库。
3. AI 内部使用结构化 JSON；用户看到的是普通语言；CSV 只属于原有导入导出路线。
4. 外部 AI 负责理解语义和作出建议，Causality 负责校验、候选检索、方案固化和事务执行。
5. MCP 不开放任意 CRUD、删除、合并或 SQL 能力。
6. 采集流程不会自动触发，必须由用户明确发起。
7. 方案审核前的提取和对比过程全部自动完成，不因存疑项中途打断用户。
8. 一次最多处理 50 个去重后的原子事件；具体案例、因果关系和案例关联不设置业务条数上限。
9. 入库是全有或全无的单事务操作，不允许部分成功。
10. 数据失败由 AI 自动修正并重新生成方案；系统失败停止自动处理并等待用户指令。

## 4. 系统边界

| 组成部分 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| 外部 AI 客户端 | 多轮对话、联网搜索、内容理解、语义判断、方案展示 | 不直接访问数据库，不绕过确认入库 |
| MCP Prompt / Markdown Prompt / 示例 Skill | 固定采集流程、确定会话范围、规范工具调用 | 不保存业务状态，不复制后端校验逻辑 |
| MCP Server | 提供查询、候选对比、方案准备和确认入库工具 | 不直接访问 PostgreSQL，不进行联网搜索 |
| Causality API | 格式与业务校验、候选检索、方案生命周期、事务入库、历史记录 | 不调用在线大模型，不代替 AI 判断语义等价 |
| Semantic Worker | 为原子事件和具体案例返回语义相似候选 | 不自动复用、合并或写入业务数据 |
| PostgreSQL | 保存业务数据、方案状态、置信度基准、令牌和成功历史 | 不保存完整对话、网页来源或 AI 推理过程 |

MCP Server 必须通过 Causality API 使用业务能力，不得绕过 API 直接访问数据库。

## 5. MCP 传输方式

### 5.1 主要方式：Streamable HTTP

- MCP Server 随 Compose 应用一起启动。
- 默认端点为 `http://127.0.0.1:8081/mcp`。
- 默认只绑定 `127.0.0.1`，不开放局域网或公网访问。
- 使用标准 Streamable HTTP。
- MCP 传输层不保存业务会话状态；方案、幂等状态和历史保存在数据库中。
- 端口允许通过 `CAUSALITY_MCP_PORT` 覆盖。

### 5.2 兼容方式：stdio

- 为只支持本地进程型 MCP 的客户端提供 stdio 入口。
- stdio 与 HTTP 共用工具注册、输入输出契约和业务实现。
- stdio 只是一种传输适配器，不形成第二套业务逻辑。

### 5.3 不采用的方式

- 不实现旧版 HTTP + SSE。
- 不实现远程公网 MCP。
- 不实现 OAuth、多租户或远程账号体系。

## 6. MCP 服务安全

HTTP MCP 服务必须：

- 校验 Bearer Token；
- 校验存在的 `Origin` 请求头，不接受未知来源；
- 只监听本机回环地址；
- 不在日志中输出完整令牌、完整候选 JSON 或会话正文；
- 为工具声明准确的只读、幂等和修改数据提示；
- 对重复提交、并发提交和客户端超时重试执行服务端幂等保护。

首次启动时生成 MCP 访问令牌并持久保存。现有“参数配置”页面新增紧凑的“MCP 服务”区域，显示：

- MCP 服务状态；
- 本机连接地址；
- 遮挡后的令牌；
- 显示或复制客户端配置；
- 重新生成令牌。

重新生成后旧令牌立即失效。stdio 入口通过本机进程或 Compose 内部网络工作，不要求用户手工填写 HTTP 令牌。

MCP 协议无法证明某一条自然语言消息确实来自用户，因此确认入库同时依赖：

1. 有效且不可变的方案编号；
2. Prompt 或 Skill 对明确确认语句的约束；
3. 客户端支持时的原生写工具审批。

核心数据安全不能依赖客户端一定实现第三项。

## 7. 会话采集范围

用户必须明确发出“采集并生成入库方案”等同义指令，系统才启动采集。

AI 自动确定范围：

1. 从当前可见会话末尾向前查找最近一次成功采集标记。
2. 找到标记时，只处理该标记之后的内容。
3. 没有标记时，从当前可见会话的最早内容开始。
4. 客户端只保留了部分上下文时，只处理可见内容，并在方案中说明范围受限。

入库成功后，AI 输出普通语言结果并附加：

```text
[Causality-Capture: AI 导入历史编号]
```

失败、回滚或取消不生成标记。成功但没有产生数据变化时仍生成标记，避免下一次重复处理同一段对话。

## 8. 提取范围与数量控制

AI 只提取与用户当前问题有关的：

- 用户关心的核心事物；
- 直接原因和连锁原因；
- 直接结果和连锁结果；
- 用于验证这些关系的具体案例。

仅用于背景说明、措辞补充或与主线没有实际因果联系的事件不得提取。

一次采集最多包含 50 个去重后的原子事件。新增和准备复用的事件均计入上限。限制在调用 MCP 前由 Prompt 或 Skill执行，API 再次强制校验。

超过 50 个时，AI 按照与用户问题的相关程度和因果链重要性保留前 50 个，并明确说明还有内容未纳入。用户可以缩小范围，或在本次成功后继续采集剩余内容。

具体案例、因果关系和案例关联不设置业务条数上限，但必须引用本次 50 个事件集合内的新事件或已有事件，不能形成悬空引用。运行环境仍保留有限的请求体大小、内存和超时保护；超过技术承载能力时整次请求失败，不进行部分处理。

## 9. AI 内部 JSON

AI 采集路线不使用 CSV。完整候选集合一次提交：

```json
{
  "atomicEvents": [],
  "concreteCases": [],
  "causalRelations": [],
  "relationCaseLinks": []
}
```

每条候选数据使用请求内唯一的临时引用，例如 `event-1`、`case-1` 和 `relation-1`。

### 9.1 原子事件候选

包含：

- 临时引用；
- 事件名称；
- 可选说明；
- 可选别名；
- 可选关键词。

### 9.2 具体案例候选

包含：

- 临时引用；
- 100 字以内的案例内容。

同一具体案例在一次采集中出现多次时先归并为一条候选，多条关系可以引用同一候选案例。

### 9.3 因果关系候选

包含：

- 临时引用；
- 原因事件临时引用；
- 结果事件临时引用；
- 可选关系说明。

AI 不提交已有关系的新置信度。关系置信度由后端规则计算。

### 9.4 案例关联候选

包含因果关系临时引用和具体案例临时引用。相同关联在候选集合内先去重。

## 10. 完整候选对比

一个 MCP 工具一次接收完整候选集合，并分类型返回结果。

| 对比对象 | 对比方式 | 结果 |
| --- | --- | --- |
| 原子事件 | 名称和别名精确匹配、普通模糊匹配、语义相似查询 | 精确结果及最多 10 条相似候选 |
| 具体案例 | 内容精确匹配、普通模糊匹配、语义相似查询，并结合时间、地点、对象和事实 | 精确结果及最多 10 条相似候选 |
| 因果关系 | 在事件身份解析后按原因、结果和方向匹配 | 已有关系、反向关系或待新增关系 |
| 案例关联 | 检查案例是否已经关联指定关系 | 已有关联或待新增关联 |

相似度只用于候选排序，不能自动决定复用。外部 AI 结合对话语境判断：

- 新增；
- 复用已有记录；
- 暂不入库。

AI 无法可靠判断时采用保守策略，将候选暂定为“不入库”，并在第一版方案中说明原因和建议，不在自动处理阶段询问用户。

语义模型、当前索引和 Semantic Worker 必须可用且索引已经完成，才能生成最终方案。模型未启用、下载中、加载失败、重新索引、索引失效或 Worker 不可用时，候选对比返回可恢复的数据准备错误，不生成最终方案。

## 11. 已有数据修改规则

### 11.1 原子事件

允许：

- 复用已有事件；
- 追加别名；
- 追加关键词；
- 替换事件说明。

禁止：

- 修改已有事件名称；
- 通过 AI 流程删除别名或关键词；
- 合并或删除事件。

替换说明时，方案必须同时展示旧说明和新说明。

### 11.2 具体案例

同一真实发生事件的不同表达复用已有案例；时间、地点、参与对象或事实不同的相似事件新增为另一条案例。

禁止修改、合并或删除已有案例内容。

当前模型没有独立的时间、地点字段，相关信息继续写入 100 字以内的案例内容。

### 11.3 因果关系

关系通过“原因事件 + 结果事件”的有向组合识别：

- 端点和方向一致时复用；
- 方向相反时视为另一条关系；
- 已有关系的原因事件、结果事件和说明不可修改；
- 允许为已有关系增加新的具体案例关联；
- AI 方案可以在正式入库前排除本次候选关联，但不能取消数据库中已有的案例关联；
- 禁止通过 AI 流程合并或删除已有关系。

## 12. 置信度规则

本阶段取消“每新增一个案例固定增加 5 个百分点”的设计。关系置信度改为由基准值和案例数量变化决定。

### 12.1 自动计算公式

```text
自动置信度 =
100 - (100 - 基准置信度) × 0.9^(当前案例数 - 基准案例数)
```

含义是每新增一个案例，只吸收当前值距离 100% 剩余差距的 10%。自动值越来越接近 100%，但不能自动成为 100%。

默认基准置信度为 10%，默认基准案例数为 0：

| 案例数 | 自动置信度 |
| ---: | ---: |
| 0 | 10.00% |
| 1 | 19.00% |
| 2 | 27.10% |
| 3 | 34.39% |
| 5 | 46.86% |
| 10 | 68.62% |
| 20 | 89.06% |

取消案例时按同一公式反向计算。恢复到基准案例数时必须准确恢复基准置信度。计算结果低于 0% 时按 0% 保存。

自动值使用高精度小数计算。有限精度存储发生向上舍入时，自动结果必须限制为该字段能够保存的最大“小于 100%”的值。手工设置为 100% 的关系在下一次案例关联变化时，计算层使用最大的小于 100% 的有效基准进行自动计算，确保自动结果仍小于 100%；原有值在没有案例变化时保持不变。

### 12.2 触发范围

任何入口造成关系与案例关联增加或取消时，都使用同一后端策略，包括：

- 普通创建和编辑页面；
- CSV 导入；
- 数据维护处理；
- AI 入库；
- 后续公开 API。

已经存在的关联不重复计算。

“取消关联后降低置信度”适用于原有人工编辑、数据维护和后续明确授权的接口。P3-01 的 AI 入库工具只允许新增关联，不获得取消数据库既有关联的权限。

### 12.3 手动修改

手动修改置信度时，将手动值和当时案例数量保存为新的基准。

同一次保存既手动修改置信度又调整案例关联时：

- 手动输入值作为本次保存的最终置信度；
- 保存完成后的案例数量成为新基准案例数；
- 只有后续案例关联再次变化时才自动计算。

新关系没有手动修改置信度时，从默认 10% 和基准案例数 0 开始，按照首次关联的案例数量自动计算。

### 12.4 现有数据迁移

迁移不立即重新计算已有关系：

- 当前置信度成为基准置信度；
- 当前关联案例数成为基准案例数；
- 当前显示值保持不变；
- 后续案例关联变化时才按新规则计算。

## 13. 入库方案生命周期

候选对比完成后，AI 提交最终判断并请求生成不可变方案。方案必须包含：

- 每个临时引用最终对应新增、复用或不入库；
- 已解析的关系端点；
- 已解析的案例关联；
- 允许的事件属性补充；
- 服务端计算的置信度变化；
- 依赖记录的版本快照；
- 方案编号、版本和过期时间。

不入库的数据不能继续被其他入库数据引用。存在未解析依赖时拒绝生成方案。

方案有效期为 30 分钟。方案状态包括：

| 状态 | 含义 |
| --- | --- |
| 有效待确认 | 可以审核、替代或确认 |
| 已被替代 | 已生成更新版本，不可提交 |
| 已失效 | 依赖数据变化，不可提交 |
| 已过期 | 超过 30 分钟，不可提交 |
| 提交中 | 正在执行事务，禁止重复提交 |
| 已完成 | 事务已成功 |
| 数据失败 | AI 可以重新查询并生成新方案 |
| 系统失败 | 等待用户决定重试或重新生成 |

每次修改要求都生成新的完整方案，旧方案立即标记为已被替代。用户审核的是完整可读方案，不显示内部 JSON 或数据库编号。

## 14. 方案审核循环

```text
用户发起采集
  → 自动提取、对比和筛选
  → 生成完整方案 V1
  → 用户提出修改建议
  → AI 重新查询、校验和计算
  → 生成完整方案 V2，V1 失效
  → 用户继续修改或明确确认
```

方案展示顺序：

1. 本次采集范围与核心问题；
2. 新增的原子事件、具体案例和因果关系；
3. 复用的已有数据；
4. 已有事件的别名、关键词和说明变化；
5. 新增的案例关联，以及从本次候选方案中排除的关联；
6. 置信度变化；
7. 暂不入库的数据及原因；
8. 数量统计和方案失效时间。

用户可以要求改变新增或复用判断、纳入或排除存疑数据、删除无关支线、修改事件说明或属性补充、调整关系及本次候选案例关联。AI 根据意见重新执行必要查询，并再次展示完整方案。该调整不能删除数据库中已经存在的案例关联。

只有“确认入库”或语义同样明确且指向最新完整方案的表达才能进入提交。普通的“好的”“继续”“看起来可以”不能触发入库。

## 15. 事务入库与幂等

确认工具接收最新方案编号。服务端提交前必须重新检查：

- 方案仍在有效期内；
- 方案仍是最新版本；
- 依赖记录未发生冲突变化；
- 业务字段和关联仍合法；
- 关系和案例关联没有形成新的重复；
- 方案尚未成功提交。

业务数据、案例关联、置信度、语义增量任务和 AI 导入历史在同一数据库事务中提交。任何一步失败全部回滚。

相同方案编号重复调用只能返回第一次成功结果，不得重复新增、重复关联或重复改变置信度。并发确认同一方案时只允许一个事务进入实际写入。

## 16. 错误分类与恢复

MCP 错误响应必须包含：

- 错误类别；
- 稳定错误代码；
- 用户可读原因；
- 受影响候选；
- AI 是否可以自动修正；
- 建议动作；
- 是否允许重试当前方案。

### 16.1 数据原因

包括方案过期、数据版本变化、候选重复、关联不存在、字段不合法、事件超过 50 个、端点冲突和依赖无法解析。

AI 自动重新查询受影响数据，根据错误修正判断并生成新的完整方案。旧方案失效，用户必须重新审核和确认。无法可靠修正的项目改为暂不入库。

### 16.2 系统或配置原因

包括 API、数据库或 MCP 不可用，事务异常，磁盘不足，连接中断，Worker 故障，权限或令牌错误，以及未知服务错误。

AI 不自动重试，必须：

- 告知用户失败阶段和原因；
- 明确本次没有数据入库；
- 提供可以理解的检查建议；
- 不写成功历史；
- 不生成成功标记；
- 等待用户要求重新尝试或重新生成。

用户要求重试时，有效且未变化的方案可以再次提交；已过期或失效的方案必须重新生成。

## 17. MCP 工具

### 17.1 只读查询

- 搜索原子事件；
- 查看原子事件和关联关系；
- 搜索具体案例；
- 查看因果关系和关联案例；
- 查询指定事件的上游、下游或双向局部因果链。

这些工具可以独立用于普通因果分析，不修改数据。

### 17.2 采集入库

- 对比完整候选集合；
- 生成不可变入库方案；
- 查询方案状态；
- 确认执行方案；
- 查询成功结果。

不提供直接创建、编辑、删除、合并或执行 SQL 的 MCP 工具。

## 18. Prompt 与 Skill

项目交付三个工作流入口：

1. 标准 MCP Prompt：通过 `prompts/list` 和 `prompts/get` 暴露；
2. 普通 Markdown Prompt：供不支持 MCP Prompt 的客户端复制使用；
3. 示例 Skill：供支持 Skill 的客户端安装。

三者引用同一份采集规范，不能分别维护业务规则。

MCP Prompt 是用户显式调用的能力，不会由服务端隐式注入。客户端可以将 Prompt 显示为 `/causality_capture`、命令面板、按钮或菜单，但斜杠命令不是协议强制界面。

Skill 不属于 MCP 通用标准。不同客户端可以自动发现、通过斜杠调用或完全不支持 Skill，因此核心流程不能只依赖 Skill。

Prompt 或 Skill 加载后，用户可以直接用自然语言要求“采集当前对话并生成入库方案”，后续只读查询、对比和方案生成工具由 AI 自动调用。

## 19. AI 导入历史

“导入导出”页面增加第三个子标签“AI 导入历史”，与“导入”和“导出”并列。

列表：

- 按完成时间倒序；
- 固定每页 50 条；
- 使用现有完整分页组件；
- 展示完成时间、采集主题、成功结果、各类数据变化和详情入口；
- 成功但无数据变化的批次显示为“成功·无变化”。

详情：

- 显示完成时间、采集主题、方案版本和可用的客户端元数据；
- 汇总原子事件、具体案例、因果关系、属性变化和案例关联；
- 按原子事件、具体案例、因果关系、案例关联和置信度变化分组；
- 长文本使用现有省略和固定大小 Tooltip 组件；
- 只读，不支持重新执行。

只保存成功批次。草稿、取消、校验失败、事务回滚、系统失败、完整对话、网页来源和 AI 推理都不进入历史。

## 20. 开发与运行

### 20.1 Compose

正式环境继续使用：

```bash
docker compose up -d --build --wait
```

该命令同时启动 MCP HTTP 服务。客户端使用本机 `/mcp` 地址和访问令牌。

### 20.2 源码开发

现有开发流程保持不变，根 `pnpm dev` 增加 MCP HTTP 开发进程。另提供：

```bash
pnpm mcp:dev
pnpm mcp:stdio
pnpm mcp:inspect
```

- `mcp:dev`：单独启动 HTTP MCP 开发服务；
- `mcp:stdio`：启动 stdio 兼容入口；
- `mcp:inspect`：使用官方 MCP Inspector 调试工具和 Prompt。

### 20.3 客户端文档

文档分别提供：

- Streamable HTTP URL 与 Bearer Token 通用配置；
- stdio 的 `command` 和 `args` 通用配置；
- Prompt 的显式调用方式；
- Markdown Prompt 的复制方式；
- 示例 Skill 的安装和调用说明；
- 不保证特定客户端一定使用 `/` 命令展示 Prompt 或 Skill。

## 21. 测试与验收

### 21.1 自动化测试

| 层级 | 内容 |
| --- | --- |
| 单元测试 | JSON 契约、50 事件上限、内部去重、关联解析、置信度公式 |
| API 集成测试 | 四类候选对比、方案生成、替代、过期、失效和重新生成 |
| 事务测试 | 全部成功、任一步失败整体回滚、历史同事务写入 |
| 幂等测试 | 重复提交、超时重试和并发提交 |
| 置信度测试 | 新增、取消、恢复案例，手动基准和现有数据迁移 |
| MCP 协议测试 | HTTP 与 stdio 共用契约，工具与 Prompt 可发现和调用 |
| 安全测试 | 缺失、错误和失效令牌，非法 Origin，本机绑定 |
| Web 测试 | MCP 设置、令牌操作、AI 历史列表、分页和详情 |
| 恢复测试 | 数据失败自动重建方案，系统失败等待用户操作 |

### 21.2 代表性容量

固定验收数据集：

- 50 个候选原子事件；
- 500 个具体案例；
- 500 条因果关系；
- 1,000 条案例关联；
- 同时包含新增、复用、语义候选、重复关联和存疑数据。

该数据集用于发现请求体、查询次数和事务性能问题，不构成具体案例或关系的业务上限。

### 21.3 人工验收

1. 使用 MCP Inspector 验证 HTTP 和 stdio。
2. 在至少一个支持 MCP 的 AI 客户端中连接 Causality。
3. 查询已有因果数据并进行多轮分析。
4. 发起采集并自动生成第一版方案。
5. 至少两次修改方案。
6. 明确确认并完成入库。
7. 检查业务数据、置信度和 AI 导入历史。
8. 再次采集并验证成功标记后的范围。
9. 制造一次数据失效并验证自动重建方案。
10. 制造一次系统故障并验证停止、提示和人工重试。

## 22. 非目标

本阶段不实现：

- 应用内在线大模型 API；
- 应用内联网搜索；
- 内置聊天页面；
- 自动触发采集；
- 保存完整对话、网页链接或 AI 推理；
- Web 待审核队列；
- 远程公网 MCP、OAuth 或多用户权限；
- AI 修改已有事件名称、案例内容、关系端点或关系说明；
- AI 合并或删除已有业务数据；
- 将 AI JSON 路线与 CSV 导入导出路线合并；
- 针对某一个 AI 客户端编写专用业务实现。
