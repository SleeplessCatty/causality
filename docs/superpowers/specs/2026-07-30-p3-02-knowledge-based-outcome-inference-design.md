# P3-02 基于知识库的结果推测设计

日期：2026-07-30
状态：开发完成，自动化测试中
前置阶段：P3-01R1 MCP 查询完整性与采集质量优化已完成

## 1. 目标

让外部 AI 客户端以一个已匹配的原子事件为起点，编排 Causality 现有只读 MCP 能力，查询最多三层下游因果网络，筛选最多五个与当前会话关注点相关的候选结果，并用可核对的路径、逐段置信度和具体案例解释推测依据。

本阶段采用 Prompt 编排方案，不新增结果聚合 API 或 MCP Tool。外部 AI 负责识别会话目标、选择与排序候选结果以及生成普通语言报告；Causality 负责提供受约束、可验证的数据库事实。

结果推测不等同于统计预测。系统不计算最终发生概率，不把关系置信度解释为结果发生概率，也不把 AI 的路径解释写回正式知识库。

## 2. 已确认原则

1. 第一版只支持单个起始事件，不处理多个事件的共同作用。
2. 默认只向下游查询三层；用户追问时，以选定结果作为新的单一起始事件重新查询。
3. 首次报告最多展示五个候选结果。
4. 没有具体案例的关系仍可参与推测，但必须明确标记“无案例依据”。
5. 候选结果先按当前会话关注点的相关性筛选，再比较路径证据和距离。
6. 不生成综合证据等级，不计算平均置信度、路径概率或最终发生概率。
7. 报告先给出简短摘要，再逐项展开候选结果。
8. 采用 Prompt、便携 Markdown Prompt 和 Codex Skill 三种同源入口。
9. 不新增结果聚合工具；为现有 `search_atomic_events` 增加可选的普通/增强搜索模式。
10. 全过程只读。保存任何新知识时，必须退出结果推测并重新进入独立的 `Causality Capture` 流程。

## 3. 方案选择

### 3.1 已采用方案

采用“Prompt 编排现有 MCP 工具”的轻量方案：

- 新增结果推测 Prompt 和 Skill；
- 使用现有事件搜索、事件详情、局部图、路径和证据工具；
- 通过 Prompt 固定调用顺序、查询上限、事实边界和输出结构；
- 不在服务端实现新的结果评分或聚合算法。

该方案开发范围小，可以先验证结果推测是否具有实际价值，并保持“应用内不接入在线 AI”的架构边界。

### 3.2 已接受限制

候选结果的语境相关性选择和排序仍由外部 AI 完成，因此不同模型的结果顺序可能略有差异。服务端 Schema、节点上限、路径上限和 Prompt 规则负责限制查询范围和事实边界，但不保证不同模型生成逐字一致的报告。

如果实际使用证明模型遗漏路径、重复调用或排序差异不可接受，再单独评估服务端结果聚合工具；该能力不属于本阶段。

## 4. 能力入口

### 4.1 MCP Prompt

新增：

```text
causality_infer_outcomes
```

Prompt 不接收业务参数，从当前可见会话识别单个起始事件、用户关心的结果方向和明确筛选要求。无法确定唯一事件时必须询问用户，不能声称读取客户端未提供的隐藏会话。

### 4.2 便携 Prompt

新增：

```text
prompts/causality-infer-outcomes.md
```

文件必须由 canonical Prompt builder 生成，并与 MCP Prompt 正文字节一致。

### 4.3 Codex Skill

新增：

```text
.agents/skills/causality-infer-outcomes/
```

Codex 展示信息：

```text
Causality Infer Outcomes
推测单个事件可能产生的后续结果
```

Skill 是薄启动器，只读取同源 Markdown Prompt 并调用 `causality` MCP 工具，不复制业务规则。

## 5. 起始事件识别与匹配

### 5.1 识别规则

AI 从当前可见会话识别一个起始事件。表达中包含多个变化时，应选择用户明确要求推测结果的事件；无法判断时先询问，不自动把多个事件组合成一个起点。

### 5.2 扩展现有事件搜索工具

现有 `search_atomic_events` 增加可选输入：

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `searchMode` | `standard \| enhanced` | `standard` | 普通或语义增强搜索 |

工具名称、只读属性和现有 `query`、`page` 输入保持不变。省略 `searchMode` 的既有客户端继续执行普通搜索。

底层复用应用已有的事件增强搜索能力，不新增数据库表、模型或索引流程。增强查询不可用时，工具返回既有语义服务原因，不静默降级并把普通结果伪装成增强结果。

### 5.3 匹配顺序

1. 使用 `searchMode = standard` 按事件名称、主体、别名或关键词搜索；
2. 普通搜索不能形成可靠匹配时，使用 `searchMode = enhanced`；
3. 取得唯一可靠候选后，调用 `get_atomic_event` 核对名称、说明、别名和关键词；
4. 存在多个无法排除的候选时，列出简短名称供用户选择；
5. 没有可靠候选时停止数据库推测，不使用模型常识替代数据库事件。

增强搜索只提供候选，不自动证明两个表达是同一事件。最终继续查询前仍由 AI 根据当前会话和事件详情消除歧义；无法消除时询问用户。

## 6. 下游图查询

匹配起始事件后，调用 `query_local_causal_graph`：

```text
direction = downstream
limit = 20
minConfidence = 0
minCaseCount = 0
```

保留最低置信度和无案例关系，是为了不在检索阶段隐藏已记录的知识；它们是否缺少证据必须在报告中如实说明。

节点扩展规则：

1. 首次查询二十个节点；
2. `stopReason` 表示达到节点限制且不足以形成五个相关候选结果时，重新查询五十个节点；
3. 五十个节点仍不足时，重新查询一百个节点；
4. 一百个节点后停止，不继续扩展；
5. 达到节点或关系限制时，报告必须说明查询结果可能不完整。

局部图按广度优先返回节点，但响应不直接提供层级。AI 必须根据返回的有向关系从起始事件重建最短层级，只保留距离起始事件不超过三段关系的节点。不能将方向相反、不可达或超过三层的节点作为候选结果。

如果已经找到五个与当前问题相关的候选结果，可以停止继续扩大节点范围；报告应在局部图未穷尽时说明候选结果不是全库穷举。

## 7. 候选结果选择

候选结果必须是返回图中从起始事件沿真实方向可达的原子事件。最多选择五个，按以下顺序判断：

1. 与当前会话关注点的相关性；
2. 是否存在完整的库内有向路径；
3. 路径逐段关系的置信度和案例情况；
4. 距离起始事件的层数。

相关性只能用于在已返回结果之间选择和排序，不能用于发明路径、跳过中间事件或把语义相似当作因果关系。

多条路径指向同一结果时，只保留一个候选结果，并在其下组织不同支持路径。直接结果和间接结果均可展示，但必须明确类型。

## 8. 路径与案例证据

### 8.1 路径验证

对每个最终候选结果调用 `find_causal_paths`：

```text
sourceEventId = 起始事件 ID
targetEventId = 候选结果 ID
maxDepth = 3
pathLimit = 10
minConfidence = 0
minCaseCount = 0
```

只接受工具实际返回的有向简单路径。AI 不得自行补充中间事件或关系。

同一结果最多展示三条支持路径：排名第一的路径完整展开，其余路径先显示事件序列摘要。工具返回截断标记时必须原样说明查询不完整。

### 8.2 关系与案例

对最终展示路径中的关系读取关系详情和案例证据。可以组合使用 `get_causal_relation`、`get_relation_cases` 或 `get_causal_evidence_bundle`，但必须满足：

- 每条关系首次最多展示三条具体案例；
- 有更多案例时显示总数，不自动全部展开；
- 没有案例时明确显示“该关系当前没有具体案例依据”；
- 同一关系被多条路径复用时，复用已读取结果，不重复解释成不同证据；
- 案例只能支持其实际关联的关系，不能跨关系迁移证据。

## 9. 固定报告结构

### 9.1 分析范围

报告首先说明：

- 起始事件；
- 查询方向为下游；
- 默认深度为三层；
- 候选结果最多五个；
- 是否达到节点、关系或路径限制。

### 9.2 结果摘要

用简短有序列表展示候选结果名称以及直接或间接类型。摘要只能说明知识库中存在通向这些结果的路径，不能声称结果一定发生。

### 9.3 候选结果详情

每个结果固定展示：

1. 结果事件名称；
2. 直接结果或间接结果；
3. 与当前问题的相关性说明；
4. 主要路径的完整事件序列；
5. 每段关系的置信度和案例数；
6. 路径中置信度最低的关系及其数值；
7. 最多三条支持路径；
8. 每段关系最多三条案例；
9. 无案例、截断或工具失败等限制。

路径最低置信度只表示该路径中数值最低的一段关系，不表示结果发生概率。报告不得计算平均置信度、关系置信度乘积或其他综合评分。

### 9.4 限制与后续追问

报告末尾集中说明本次查询边界，并提供少量后续方向：

- 以某个候选结果为新的起始事件继续分析；
- 完整展开某条备选路径；
- 查看某段关系的更多具体案例；
- 检查候选结果是否还有其他已知原因。

后续扩展必须发起新的受限查询，不能在首次报告中无限展开。

## 10. 事实与推测边界

数据库事实包括：

- 原子事件名称与详情；
- 已记录的因果关系；
- 关系置信度；
- 关联具体案例；
- 工具实际返回的有向路径和截断状态。

AI 推测包括：

- 哪些结果与当前问题最相关；
- 五个结果的选择与排序；
- 对已存在路径作用机制的普通语言解释；
- 建议用户继续追问的方向。

报告必须用措辞区分两者。AI 不得把解释描述为数据库字段、把未记录的常识描述为库内路径，或把置信度描述为统计概率。

## 11. 外部信息规则

默认只使用 Causality 数据库。用户明确要求结合网络资料时，外部 AI 可以增加独立的“外部信息补充”章节，但必须：

- 与“Causality 库内依据”分开；
- 不用外部信息补齐不存在的库内路径；
- 不把网页内容描述为数据库具体案例；
- 不通过结果推测流程直接写入新发现；
- 用户要求保存时，重新启动 `Causality Capture`。

本阶段不为 MCP Server 增加联网搜索、网页抓取或来源保存能力。

## 12. 工具权限边界

结果推测允许编排以下只读工具：

- `search_atomic_events`
- `get_atomic_event`
- `query_local_causal_graph`
- `get_causal_relation`
- `get_relation_cases`
- `get_concrete_case`
- `find_causal_paths`
- `get_causal_evidence_bundle`

根据需要可读取具体案例详情，但不得为了结果推测调用采集工具。明确禁止：

- `compare_knowledge_candidates`
- `prepare_knowledge_changes`
- `commit_knowledge_changes`
- `get_import_plan_status`
- `get_import_result`

用户要求保存结果时，当前 Prompt 停止并提示切换到采集 Skill；不能把推测内容直接交给提交工具。

## 13. 异常处理

| 情况 | 处理方式 |
| --- | --- |
| 起始事件有多个可靠候选 | 暂停并要求用户选择 |
| 普通和增强搜索均无可靠匹配 | 停止数据库推测 |
| 增强查询不可用 | 说明语义服务原因，允许用户选择普通候选或停止 |
| 没有下游关系 | 明确说明知识库中暂无可推测结果 |
| 达到节点、关系或路径限制 | 返回已有结果并说明可能不完整 |
| 单条关系没有案例 | 保留关系并标记无案例依据 |
| 部分工具调用失败 | 标出失败范围，不把部分结果描述为完整结果 |
| MCP Server 不可用 | 停止并提示检查服务和客户端配置 |
| 用户要求写入推测结果 | 切换到独立采集流程，不直接写库 |

工具失败后不得以模型常识伪造缺失响应。已经取得的部分结果可以展示，但必须明确其范围。

## 14. 交付范围

### 14.1 新增

- 一个 MCP Prompt；
- 一个同源 Markdown Prompt；
- 一个 Codex Skill 及统一展示元数据；
- Prompt 注册、能力清单和服务端说明；
- 使用文档与人工验收说明。

### 14.2 修改

- `search_atomic_events` 增加兼容的 `searchMode` 可选输入；
- MCP API client 复用现有普通和增强事件搜索端点；
- 能力 manifest 中 Prompt 数量从四个变为五个；
- HTTP 与 stdio 继续由同一 Server 工厂发布相同能力。

### 14.3 不包含

- 新的 MCP Tool；
- 结果聚合 API；
- 数据库迁移；
- Web 页面；
- 应用内在线 AI；
- 推测历史记录；
- 多起始事件共同作用；
- 自动保存推测结果；
- 综合证据等级或结果概率；
- 股票价格、涨跌幅或目标价预测；
- 自动联网搜索。

完成后稳定能力数量为十五个工具、五个 Prompt、四个 Resource 和五个 Codex Skill。

## 15. 自动化验证

### 15.1 事件搜索兼容性

- 省略 `searchMode` 时仍执行普通搜索；
- `standard` 与 `enhanced` 分别调用正确端点；
- 非法模式和未知字段在请求 API 前拒绝；
- 增强服务未就绪、索引生成中和服务失败返回可读原因；
- HTTP 与 stdio 的输入 Schema 一致；
- 不影响现有分页行为。

### 15.2 Prompt 与 Skill

- 第五个 Prompt 正确注册且无业务参数；
- MCP Prompt 与 Markdown Prompt 字节一致；
- Skill 读取对应 Markdown，不复制业务规则；
- Codex 展示名称和中文用途符合统一格式；
- Prompt 只包含允许的只读工具并明确拒绝五个采集工具；
- 默认三层、二十至一百节点扩展、五个结果、三条路径和每段三条案例均有断言；
- Prompt 禁止综合等级、平均值、乘积和发生概率；
- Prompt 包含事实边界、外部信息分区和截断措辞。

### 15.3 协议与回归

- MCP 能力清单准确包含十五个工具、五个 Prompt 和四个 Resource；
- Streamable HTTP 与 stdio 均能列出和读取第五个 Prompt；
- 能力 Resource 与实际注册结果一致；
- 既有采集、事件分析、路径追踪和因果链审查不变；
- 结果推测读取过程不调用方案准备或提交接口；
- 全仓 lint、格式、类型检查、单元测试、构建和 Compose 合约门禁通过。

## 16. 人工验收场景

1. 唯一匹配的起始事件；
2. 多个相似事件，需要用户选择；
3. 普通搜索失败、增强搜索成功；
4. 增强服务不可用；
5. 普通和增强搜索均无匹配；
6. 只有直接结果；
7. 同时存在直接和间接结果；
8. 多条路径指向同一结果；
9. 路径中存在无案例关系；
10. 达到二十、五十或一百节点限制；
11. 路径查询被截断；
12. 用户追问某个候选结果；
13. 用户要求查看更多案例；
14. 用户明确要求结合外部资料；
15. 用户要求把推测结果写入数据库。

验收时应确认报告始终区分库内事实和 AI 推测，没有整体概率，没有自动写库，也没有绕过 `Causality Capture` 的确认门禁。

## 17. 建议实施顺序

1. 扩展原子事件 MCP 搜索模式并完成兼容回归；
2. 建立结果推测共享常量和 canonical Prompt builder；
3. 注册第五个 MCP Prompt 并同步便携 Markdown；
4. 增加 Codex Skill 和统一展示元数据；
5. 更新能力 manifest、Resource、Server instructions 和传输测试；
6. 更新 README、用户指南和人工验收步骤；
7. 执行全仓发布候选验证并进入人工复核。

该顺序只用于说明依赖关系。详细文件、测试和提交步骤将在设计文档审核通过后单独编写实施计划。
