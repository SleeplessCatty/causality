# P3-01R1 MCP 查询完整性与采集质量优化设计

日期：2026-07-29
状态：设计审核通过；Task 1 已完成；Task 2 已实施，等待人工复核

## 1. 目标

在现有 11 个 MCP 工具、`causality_capture` Prompt、Streamable HTTP 与 stdio 入口基础上，补齐查询续页能力，提升 AI 会话采集的主线相关性、原子事件精度和因果关系合理性，并增加供外部 AI 查询路径和证据的只读能力。

本步骤继续遵守“外部 AI 负责理解与建议，Causality 负责结构校验、库内对比和受控写入，用户负责最终确认”的边界。

## 2. 原子事件定义

原子事件的原子性相对于当前讨论语境和知识建模目的判断，不等同于完全抽象化。

原子事件：

- 可以包含真实主体，例如“阿里巴巴美股股价上升”“特斯拉汽车销量下滑”；
- 可以包含限定主体范围的定语，例如“国内融资成本上升”；
- 必须细粒度、方向明确并精准表达当前会话实际讨论的内容；
- 只表达一个可以独立作为因果关系端点的状态、动作或变化；
- 如果一句表达包含两个能够分别成为关系端点的事件，则必须拆分；
- 不为了追求复用而删除会改变当前讨论含义的主体或限定语。

例如，“美联储提高政策利率并导致美国企业融资成本上升”应拆为“美联储政策利率上升”和“美国企业融资成本上升”，再建立有向关系。

## 3. 主线相关性

每次采集先确定用户关心的主题锚点和原因、结果或双向追溯方向。

- 候选原子事件必须位于与主题锚点相关的原因链或结果链上；
- 只提供背景说明、没有进入主线因果链的内容不采集；
- 每个候选原子事件必须至少作为一条候选因果关系的端点；
- 每个候选具体案例必须至少支持一条候选因果关系；
- 无法可靠判断是否属于主线时采用保守策略，不依靠想象补充。

## 4. 直接关系与间接关系

因果关系必须有会话中的明确事实、具体案例或用户明确陈述作为依据。逻辑上可能、时间上同时发生或常识上看似合理均不足以建立关系。

- 信息只支持 `A → B → C` 时，只建立 `A → B` 和 `B → C`；
- 只有存在独立依据支持 A 直接导致 C 时，才同时建立 `A → C`；
- 中间事件已经出现在会话事实或明确机制中时，应提取为原子事件；
- 怀疑存在中间事件但无法从当前可见内容确认时，不得自行发明，应跳过相关关系或等待用户补充；
- 已有关系仍按端点和方向复用，质量规则不得变相修改已有关系。

## 5. 实施任务与顺序

### Task 1：现有查询分页与游标完整性

- 为原子事件搜索和具体案例搜索增加明确分页输入；
- 为关系案例查询增加游标输入，使返回的 `nextCursor` 可以继续使用；
- 保持现有默认返回数量和只读属性；
- 为 HTTP 与 stdio 共用契约补齐自动化测试和手工调用说明。

Task 1 保持原工具名称不变，新增的可选输入如下：

| 工具 | 新增输入 | 默认值 | 约束 |
| --- | --- | --- | --- |
| `search_atomic_events` | `page` | `1` | `1..100000` |
| `search_concrete_cases` | `page` | `1` | `1..100000` |
| `get_relation_cases` | `caseLimit` | `20` | `1..100` |
| `get_relation_cases` | `caseCursor` | 无 | 使用上次响应的 `nextCursor`，最长 2000 字符 |

在 MCP Inspector 或任意支持工具调用的客户端中，可以依次使用以下参数进行人工复核：

```json
{"query":"供应链","page":2}
```

```json
{"query":"港口停运","page":2}
```

```json
{"relationId":"<因果关系 UUID>","caseLimit":20,"caseCursor":"<上次返回的 nextCursor>"}
```

首次调用可以省略 `page`、`caseLimit` 和 `caseCursor`。HTTP 与 stdio 入口使用同一个 MCP Server 工厂和同一组 Schema，因此参数、默认值和输出一致。

### Task 2：统一采集规范与 V2 Prompt

- 将本文件中的原子事件、主线相关性和直接/间接关系规则写入唯一规范源；
- MCP Prompt、便携 Markdown Prompt 和示例 Skill 继续引用同一规范，不分别维护业务规则；
- AI 调用对比工具前执行完整候选自检；
- 质量依据不足的内容不得进入候选集合；内容有效但无法判断新增或复用时使用 `skip`，不得用推测填补缺失事实；
- 首次完整方案前由 AI 自动完成全部决策，并将提取结果按确信数据、存疑数据和忽略数据展示给用户；
- 保留现有自动生成方案、修改循环、明确确认和成功标记流程。

### Task 3：服务端候选质量门禁

- 候选对比在执行库内搜索前后返回结构化质量问题；
- 硬错误阻止生成入库方案，警告允许 AI 修正后重新对比；
- 检查引用完整性、批次内重复、孤立候选、明显复合事件、自环和缺少支持的关系；
- 对可能把间接关系压缩为直接关系的候选给出可修复提示；
- 本地语义模型只辅助相似性和主题相关性判断，不负责证明因果关系；
- 使用版本化严格 JSON Schema 和字段级错误路径，非法数据不得进入正式知识表。

### Task 4：只读查询与证据工具

按以下顺序增加深接口：

1. 具体案例详情及其关联关系；
2. 因果关系搜索；
3. 两个原子事件之间的受限因果路径；
4. 包含路径、关系和具体案例的因果证据包。

适用搜索可选择普通或现有本地语义增强模式。所有工具必须具有明确数量、深度、分页或游标限制，不增加通用写能力。

### Task 5：分析 Prompt 与 Resource

- 增加事件原因与结果分析 Prompt；
- 增加因果路径追踪和因果链审查 Prompt；
- 增加领域规则、采集规则、能力清单和本地系统状态只读 Resource；
- Prompt 只编排只读查询，推测结果不自动写入正式知识库；
- 客户端不支持 MCP Prompt 或 Resource 时，核心工具仍可独立使用。

## 6. 明确不包含

- 跨模型采集质量测试集；
- 应用内在线 AI 模型接口；
- 自动网页抓取或来源信息持久化；
- 通用创建、编辑、删除、合并或 SQL MCP 工具；
- AI 绕过不可变方案和用户确认直接写库；
- 自动训练模型或自动修改既有原子事件名称、案例内容和关系端点。
