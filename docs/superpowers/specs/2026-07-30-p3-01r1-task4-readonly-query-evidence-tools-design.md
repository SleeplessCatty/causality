# P3-01R1 Task 4 只读查询与证据工具设计

日期：2026-07-30
状态：设计审核通过，实施计划等待审核

## 1. 目标

在现有 11 个 MCP 工具和 Causality API 之上增加四个边界明确的只读工具，使外部 AI 能够读取具体案例详情、搜索因果关系、查询两个原子事件之间的受限有向路径，并把用户选中的路径展开为可核对的证据包。

本任务只增强查询和证据读取能力，不修改现有采集入库事务，不增加通用写、删除、合并、SQL、网页抓取或应用内在线 AI 能力。

## 2. 已确认原则

1. 新能力拆分为四个独立 MCP 工具，不使用多模式综合工具。
2. 现有 11 个工具的名称、输入和输出保持兼容；完成后工具总数为 15。
3. 普通搜索仍是默认行为，只有调用方明确指定时才执行现有本地语义增强搜索。
4. 路径只沿数据库中的真实因果方向查询，不把反向遍历当成因果路径。
5. 路径结果必须受深度、数量、筛选条件和内部扩展上限约束。
6. 证据包只展开调用方从路径结果中选中的一条路径，不替调用方重新选择路径。
7. 没有关联具体案例的关系可以出现在路径中，但必须明确标记为“无案例依据”。
8. MCP Server 只负责严格 Schema、API 调用和可读摘要，不自行计算路径或推断因果事实。

## 3. 工具清单

| 工具 | 作用 | 主要数据源 |
| --- | --- | --- |
| `get_concrete_case` | 读取具体案例详情及分页关联关系 | 现有案例详情和案例关系 API |
| `search_causal_relations` | 普通或显式增强搜索因果关系 | 现有关系列表服务 |
| `find_causal_paths` | 查询两个事件间的受限有向简单路径 | 新增只读路径服务 |
| `get_causal_evidence_bundle` | 展开一条已选择路径的关系和案例依据 | 新增只读证据包服务 |

四个工具都标记为只读、非破坏、幂等且不访问开放网络。Streamable HTTP 与 stdio 继续使用同一个 MCP Server 工厂和同一组 Schema。

## 4. `get_concrete_case`

### 4.1 输入

- `caseId`：具体案例 UUID；
- `relationLimit`：本次关联关系数量，默认 20，范围 1–100；
- `relationCursor`：可选续页游标，最大 2,000 字符。

### 4.2 输出

- 案例 ID、内容、创建时间和更新时间；
- 数据库中的关联关系总数；
- 本批关联关系；
- `hasMore` 和 `nextCursor`。

每条关联关系包含关系 ID、原因事件、结果事件和案例关联时间。实现复用现有 `GET /api/cases/:caseId` 与 `GET /api/cases/:caseId/relations`，由 MCP API 客户端并行读取并组合，不复制数据库查询逻辑。

## 5. `search_causal_relations`

### 5.1 输入

- `query`：搜索词，去除首尾空白后长度 1–120；
- `searchMode`：`standard` 或 `enhanced`，默认 `standard`；
- `page`：页码，默认 1，范围 1–100,000。

### 5.2 行为与输出

普通搜索匹配原因事件名、结果事件名和关系说明。增强搜索显式复用现有本地语义查询能力；模型未加载或索引未就绪时返回现有结构化不可用原因，不自动降级为普通搜索。

输出沿用现有关系列表分页结构，包含：

- 关系 ID；
- 原因事件和结果事件的 ID、名称；
- 置信度、案例数和更新时间；
- 当前页、总页数和总条目数；
- 可选语义索引提示。

API 继续使用现有 `GET /api/relations`，MCP 只增加对应只读入口。

## 6. `find_causal_paths`

### 6.1 输入

- `sourceEventId`：起点原子事件 UUID；
- `targetEventId`：终点原子事件 UUID；
- `maxDepth`：最大关系层数，默认 5，范围 1–10；
- `pathLimit`：最多返回路径数，默认 10，最大 10；
- `minConfidence`：最低置信度，默认 0，范围 0–100；
- `minCaseCount`：最少案例数，默认 0，范围 0–1,000。

起点和终点必须存在且不能相同。

### 6.2 路径语义

- 只沿 `causeEvent → effectEvent` 方向扩展；
- 每条结果都是简单路径，同一事件或关系不能在路径内重复；
- 关系必须同时满足最低置信度和最少案例数；
- 空结果是成功响应，表示当前条件下不存在可达路径；
- 不计算或返回未受约束的“完整匹配数量”。

### 6.3 排序

路径使用稳定且可解释的排序：

1. 跳数少的路径优先；
2. 同跳数时，案例总数高的优先；
3. 仍相同时，路径最低置信度高的优先；
4. 最后按有序关系 ID 序列进行确定性排序。

每条路径返回有序事件、有序关系、跳数、最低置信度和案例总数。

### 6.4 查询保护

路径服务按层执行受限有向搜索，不把整张因果图加载到 Node.js 内存。单次查询最多探索 10,000 个候选路径状态。

响应包含：

- `truncated`：结果是否可能不完整；
- `truncatedReason`：`path_limit`、`expansion_limit` 或 `null`；
- `expandedStateCount`：实际探索的候选状态数量。

触发 10,000 状态保护时返回已经找到的路径，并明确标记 `expansion_limit`，不把不完整结果描述为完整搜索结果。

## 7. `get_causal_evidence_bundle`

### 7.1 输入

- `relationIds`：1–10 个按路径顺序排列的关系 UUID；
- `caseLimitPerRelation`：每条关系返回的案例数量，默认 5，范围 1–20。

### 7.2 服务端校验

服务端基于当前数据库状态重新校验：

- 所有关系都存在；
- 前一关系的结果事件等于后一关系的原因事件；
- 关系方向与输入顺序一致；
- 没有重复关系；
- 有序关系不会形成事件循环。

路径查询与证据包调用之间若数据已变化，证据包返回“路径已变化”的可修复错误，要求调用方重新查询路径。

### 7.3 输出

证据包返回：

- 完整的有序事件序列；
- 完整的有序关系序列；
- 每条关系的说明、置信度和案例总数；
- 每条关系最近关联的案例，默认 5 条；
- `returnedCaseCount` 和 `casesTruncated`；
- 整条路径的跳数、最低置信度和案例总数。

每条案例包含案例 ID、内容和关联时间。若关系没有案例，返回空数组和明确的“无案例依据”状态。需要更多案例时，调用方继续使用现有 `get_relation_cases` 游标工具。

## 8. API 与模块边界

### 8.1 复用接口

- 案例详情：`GET /api/cases/:caseId`；
- 案例关联关系：`GET /api/cases/:caseId/relations`；
- 因果关系搜索：`GET /api/relations`。

### 8.2 新增接口

- `GET /api/causal-paths`：接收起点、终点、深度、数量和关系筛选参数；
- `POST /api/causal-evidence-bundles`：请求体传递有序关系 ID 和案例限制。

证据包使用 POST 只是为了安全承载有序数组和严格请求体，业务语义仍是只读、幂等和非破坏。

### 8.3 深模块

新增只读 `CausalPathService` 和 `CausalEvidenceBundleService`：

- 路径服务负责事件校验、分层遍历、循环防护、稳定排序和截断元数据；
- 证据包服务负责有序路径校验、只读快照和可读证据组装；
- PostgreSQL repository 负责受筛选的邻接边批量读取和关系/案例批量读取；
- Contracts 定义 API 唯一输入输出结构；
- MCP 维护严格镜像 Schema，不直接复用带 transform 的 Zod Schema 生成线上 JSON Schema。

## 9. 一致性与性能

1. 路径扩展使用原因事件、结果事件和关系案例计数相关索引，不执行逐路径 N+1 查询。
2. 每一层按当前 frontier 批量读取邻接关系，并在服务层维护路径内已访问事件集合。
3. 证据包在同一个只读数据库快照中批量读取关系、事件、案例和关联时间。
4. 证据包必须重新验证路径，不信任 MCP 客户端提交的关系顺序。
5. 不增加新的数据库业务表；只有在执行计划证明现有索引不足时，才增加针对只读查询的迁移索引。

## 10. 错误处理

| 情况 | 结果 |
| --- | --- |
| 起点或终点不存在 | 结构化事件不存在错误 |
| 起点和终点相同 | 字段级参数错误 |
| 当前条件下没有路径 | 成功响应，`paths` 为空 |
| 增强模型或索引不可用 | 现有语义服务不可用错误，不自动降级 |
| 证据包关系不存在 | 指出缺失关系 ID |
| 关系顺序错误或不连续 | 字段路径和重新排序建议 |
| 路径重复或形成循环 | 字段路径和移除重复关系建议 |
| 路径查询后数据变化 | 要求重新查询路径 |
| 数据库或系统异常 | 不可由 AI 修复的系统错误 |

MCP 普通文本只解释服务端结果，不把系统错误改写成“没有路径”。结构化错误继续保留错误代码、可修复性和受影响字段。

## 12. 人工验收

1. 查询具体案例，并通过游标读取下一批关联关系；
2. 对同一关键词分别执行普通和增强关系搜索；
3. 查询一条直接路径、一条多层路径和一组无路径事件；
4. 调整最低置信度和最少案例数，确认路径相应变化；
5. 从路径结果选择一条关系序列并生成证据包；
6. 提交顺序错误或不连续的关系 ID，确认返回可修复提示；
7. 确认无案例关系明确显示没有案例依据；
8. 确认所有操作都没有新增、编辑或删除数据库记录。

## 13. 明确不包含

- 应用内在线 AI、联网搜索和来源信息持久化；
- 通用新增、编辑、删除、合并或 SQL 工具；
- AI 自动选择路径并把推测写入正式知识库；
- Web 页面改造；
- 无限制路径枚举或全图导出。
