# P3-01R1 Task 5 分析 Prompt 与只读 Resource 设计

日期：2026-07-30
状态：设计内容已确认，等待正式文档审核
所属阶段：P3-01R1 MCP 查询完整性与采集质量优化
前置能力：15 个 MCP 工具、`causality_capture` Prompt、Streamable HTTP 与 stdio 入口

## 1. 目标

在 Task 4 已交付的只读查询与证据工具之上，增加三个用途明确的分析 Prompt 和四个固定只读 Resource，使外部 AI 能够从当前可见会话识别分析目标，自动读取 Causality 数据库中的事件、关系、路径和案例，并输出结构稳定、证据边界清楚的普通语言报告。

Task 5 只编排现有只读能力。它不修改正式知识库，不生成入库方案，不接入应用内在线 AI，也不把 AI 推测伪装成数据库事实。客户端不支持 MCP Prompt 或 Resource 时，现有工具、便携 Markdown Prompt 和轻量 Skill 仍可独立使用。

## 2. 已确认原则

1. 分析入口拆为三个独立 Prompt，不使用一个多模式综合 Prompt。
2. Prompt 不接收业务参数，从当前可见会话判断目标、方向和链路；无法消除事件歧义时询问用户。
3. 数据库中没有可靠匹配事件时停止数据库分析，不自动选择相似事件，也不使用模型常识补齐。
4. 事件分析默认只展示直接关系，用户追问后才逐层扩展。
5. 每条已展示关系最多返回 3 个具体案例；无案例时明确写“无案例依据”。
6. 路径追踪最多展示 3 条路径，完整展开排名第一的路径，其余路径先显示摘要。
7. 没有直接关系但存在中间路径时，只标记为“仅有间接路径支持”，不能据此认定直接关系成立。
8. 因果链按相邻关系逐段审查并总结最弱环节，不生成整条链的真假评分。
9. 多段路径不计算平均置信度或整体发生概率，只报告逐段置信度和路径最低置信度。
10. 默认只依据 Causality 数据库；只有用户明确要求时才增加独立的外部信息章节。
11. 三个分析流程同时提供 MCP Prompt、便携 Markdown Prompt 和轻量 Skill。
12. 分析目标明确后自动完成全部只读查询，只有事件歧义无法消除时才暂停。
13. Resource 拆为领域规则、采集规则、能力清单和实时系统状态四项。
14. 分析 Prompt 与 Resource 不能成为现有采集确认门禁的旁路。

## 3. 总体架构

采用“共享规范内核 + 三个独立 Prompt”的结构：

- 共享分析规范只定义事实边界、事件匹配、案例证据、外部信息分区、截断表达和只读安全规则；
- 每个 Prompt 在共享规范之上增加自己的工具编排流程与报告模板；
- 每个 Prompt 最终生成一份自包含指令，不要求客户端先读取 Resource；
- Markdown Prompt 由对应 canonical builder 生成，并与 MCP Prompt 内容保持字节一致；
- Skill 是薄启动器，只引用对应 MCP Prompt 和 Markdown 路径，不复制业务规则；
- Resource 是可选的规则与状态入口，不是 Prompt 正常运行的前置依赖。

MCP Server 继续由同一个工厂注册工具、Prompt 和 Resource。Streamable HTTP 与 stdio 必须暴露完全相同的 15 个工具、4 个 Prompt 和 4 个 Resource。

本任务不增加数据库业务表或迁移。系统状态 Resource 复用现有健康、就绪和语义生命周期 API。

## 4. Prompt 清单与通用契约

| Prompt | 作用 | 参数 |
| --- | --- | --- |
| `causality_analyze_event` | 分析当前会话所关注事件的直接原因或直接结果 | 无 |
| `causality_trace_path` | 追踪当前会话中两个事件之间的有向因果路径 | 无 |
| `causality_review_chain` | 审查用户提出的因果链及每一段的库内支持情况 | 无 |

三个 Prompt 都返回一条包含完整规范的用户消息。Prompt 不声明业务参数；分析对象、方向、筛选要求和用户明确给出的深度要求从当前可见会话读取。Prompt 不能声称读取客户端未提供的隐藏历史。

三个 Prompt 只允许编排以下十个知识与证据工具：

- `search_atomic_events`
- `get_atomic_event`
- `search_concrete_cases`
- `get_causal_relation`
- `get_relation_cases`
- `query_local_causal_graph`
- `get_concrete_case`
- `search_causal_relations`
- `find_causal_paths`
- `get_causal_evidence_bundle`

分析流程不得调用以下采集工具：

- `compare_knowledge_candidates`
- `prepare_knowledge_changes`
- `commit_knowledge_changes`
- `get_import_plan_status`
- `get_import_result`

用户在分析后明确要求采集时，AI 必须重新启动独立的 `causality_capture` 流程，不能把当前分析结果直接写库。

## 5. 共享分析规范

### 5.1 目标识别与事件匹配

AI 先从当前可见会话识别用户关心的主题、事件、原因或结果方向。事件匹配按以下顺序执行：

1. 使用普通搜索查询原子事件；
2. 普通搜索无法形成可靠唯一候选时，自动执行增强搜索；
3. 多个候选在主体、范围、状态、方向或粒度上仍无法区分时，向用户展示简洁名称并请用户选择；
4. 普通和增强搜索都没有可靠候选时，停止数据库分析；
5. 增强查询不可用时说明原因，可以继续使用已经取得的普通搜索结果，但不能声称增强查询成功。

相似只表示候选，不自动表示同一事件。AI 不得为了继续流程而忽略真实主体、限定范围、状态方向或粒度差异。

### 5.2 数据库事实与证据边界

- 原子事件、因果关系、置信度、案例数和具体案例只按工具实际返回内容描述；
- 关系存在不等于已经得到案例支持；
- 案例数只表示当前关联记录数量，不代表相互独立的统计样本数量；
- 无案例关系只能写“库内有关系记录，但无案例依据”；
- 仅有时间先后、共同出现、模型常识或外部相关性不能替代库内因果关系；
- 路径排名只表示服务端排序靠前，不表示该路径一定是真实原因；
- 路径最低置信度用于识别最薄弱关系，不是整体结果发生概率；
- 禁止使用“已经证实”“必然导致”“一定发生”等超出数据库能力的措辞。

### 5.3 外部信息分区

默认报告只依据 Causality 数据库。用户明确要求联网补充时，AI 可以使用客户端自己的联网能力，但必须在报告末尾增加独立的“外部信息”章节，并遵守：

- 明确说明内容不来自 Causality 数据库；
- 能够引用来源时给出来源；
- 不使用外部信息改写库内关系、置信度或案例状态；
- 不通过分析 Prompt 自动进入采集入库流程；
- 联网失败不影响已经完成的库内报告。

## 6. `causality_analyze_event`

### 6.1 查询流程

1. 从会话判断目标事件以及原因、结果或双向分析意图；意图无法判断时先询问用户。
2. 按共享匹配规则确定一个数据库原子事件。
3. 读取事件关系总数，并查询当前方向的局部因果图。
4. 只保留与中心事件直接相邻且方向正确的关系，不自动展示第二层。
5. 单次最多检查 100 条返回的直接关系；超出检查范围时必须披露。
6. 按案例数降序、置信度降序和关系 ID 稳定排序，首次选择前 5 条。
7. 对已选择关系读取关系详情和最多 3 个最新关联案例。
8. 用户追问时才继续展示其他直接关系，或沿用户指定关系扩展下一层。

如果用户在会话中明确要求最低置信度、最少案例数或单向范围，Prompt 在现有工具上限内尊重该要求；没有明确要求时使用工具默认筛选值。

### 6.2 输出结构

1. 分析目标；
2. 库内结论；
3. 直接关系；
4. 案例依据；
5. 不确定性与限制；
6. 可继续追问。

直接关系必须显示相关事件、真实方向、关系置信度、案例总数和证据状态。报告说明关系总数、本次检查数量、首次展示数量及剩余未展开数量；如果只检查了总关系的一部分，不能把未检查关系称为不存在。

## 7. `causality_trace_path`

### 7.1 查询流程

1. 从会话识别起点和终点，并分别完成可靠事件匹配；
2. 按起点到终点的真实因果方向查询，不进行反向推断；
3. 默认使用 `maxDepth = 5`、`pathLimit = 10`、`minConfidence = 0`、`minCaseCount = 0`；
4. 用户明确提出合法筛选或深度要求时，在工具允许范围内覆盖默认值；
5. 首次报告最多选择服务端排序前 3 条路径；
6. 对排名第一的路径读取完整证据包，每段最多返回 3 个案例；
7. 另外两条只显示事件链、跳数、路径最低置信度和案例总数；
8. 用户追问其他路径时再读取对应证据包。

### 7.2 输出结构

1. 追踪目标；
2. 主要路径；
3. 逐段证据；
4. 其他候选路径；
5. 路径限制；
6. 可继续追问。

逐段证据显示关系说明、置信度、案例总数和最多 3 个案例。没有案例的段落必须明确写“无案例依据”。查询达到路径数上限或 10,000 个扩展状态时，报告首段说明结果不完整。

没有找到路径且 `truncated = false` 时，可以写“当前筛选和最大深度下未找到路径”；没有找到路径但结果被截断时，只能写“当前受限查询尚未找到路径，仍可能存在未展开路径”。

## 8. `causality_review_chain`

### 8.1 查询流程

1. 从会话提取用户主张的有向事件链；
2. 对链中每个事件完成可靠匹配；
3. 单次最多审查 10 个相邻关系段，超过时明确分批并等待继续；
4. 对每一段先检查同方向直接关系及案例；
5. 没有直接关系时，查询包含中间事件的有向路径；
6. 同时检查是否只存在反向直接关系；
7. 每个实际展开的直接关系或间接路径段最多读取 3 个案例；
8. 按原链顺序输出逐段结果并总结最弱或断裂位置。

### 8.2 逐段分类

每一段使用以下五种主要分类之一：

1. **库内有直接关系与案例依据**；
2. **库内有直接关系，但无案例依据**；
3. **仅有间接路径支持**；
4. **只存在反向关系**；
5. **库内未找到支持**。

判断优先级：

- 同方向直接关系存在时，根据案例状态使用分类 1 或 2；
- 没有直接关系但存在有向路径时使用分类 3，并展示必要中间事件；
- 分类 3 同时发现反向直接关系时，额外增加方向风险提示，但主要分类仍为“仅有间接路径支持”；
- 没有同方向直接或间接路径、但存在反向关系时使用分类 4；
- 以上均不存在时使用分类 5。

分类 3 不能用来证明原始直接关系。报告应建议把 `A → B` 改写为数据库实际支持的 `A → X → B`。

### 8.3 输出结构

1. 审查对象；
2. 逐段审查；
3. 薄弱与断裂位置；
4. 案例依据；
5. 审查限制；
6. 修改建议。

报告不生成整条链的真、假、概率或模型评分。总结只说明哪些段有直接案例支持，哪些段无案例、仅间接支持、方向相反或缺少库内依据。

## 9. 统一用户可读输出规范

三个 Prompt 都输出固定章节的普通语言报告，不直接展示工具 JSON。默认不显示数据库 UUID；只有排查歧义或用户明确要求时才显示 ID。

共同要求：

- 事件和案例使用完整可读名称或内容；
- 工具返回的案例时间信息保留在案例描述中，不编造缺失时间；
- 每项结论能对应到关系或路径；
- 数据读取失败与证据不存在使用不同措辞；
- 对路径截断、案例截断、关系检查上限和链段上限明确披露；
- 对可继续执行的查询给出简短追问方向，不自动启动另一项分析或采集流程。

## 10. Resource 清单

| URI | MIME 类型 | 内容 |
| --- | --- | --- |
| `causality://rules/domain-model` | `text/markdown` | 领域数据类型、直接与间接关系及证据边界 |
| `causality://rules/capture` | `text/markdown` | 当前 V2 会话采集与受控入库规范 |
| `causality://capabilities` | `application/json` | 工具、Prompt、Resource 和主要限制 |
| `causality://system/status` | `application/json` | 本地 API、数据库、语义 Worker、模型和索引状态 |

四个 Resource 使用固定 URI，不引入参数化 Resource Template。

### 10.1 领域规则 Resource

领域规则由共享规范源生成，至少包含：

- 语境化原子事件定义；
- 具体案例真实性边界；
- 直接关系和间接路径区别；
- 置信度、案例数和路径最低置信度含义；
- 无案例关系的正确表达；
- 数据库事实、AI 推测和外部信息边界。

### 10.2 采集规则 Resource

采集规则复用当前 canonical V2 采集规范。读取 Resource 只返回规则文本，不启动采集、不生成候选、不创建方案。

### 10.3 能力清单 Resource

能力清单使用严格、带版本号的 JSON，至少包含：

- `schemaVersion`；
- MCP Server 名称和版本；
- 15 个工具的名称、用途和只读或受控写入属性；
- 4 个 Prompt 名称；
- 4 个 Resource URI；
- 路径、深度、扩展状态、案例和分析展示主要上限；
- 不支持 Prompt 或 Resource 的客户端兼容说明。

工具、Prompt、Resource 名称和数量由统一能力 manifest 提供给注册代码、Resource 和回归测试，避免手工维护的清单漂移。manifest 不包含访问令牌、内部 URL 或运行环境配置。

### 10.4 系统状态 Resource

系统状态每次读取时实时并行检查：

- MCP Server 名称、版本和在线状态；
- Causality API 健康状态；
- PostgreSQL 就绪状态；
- 语义 Worker 可达和模型加载状态；
- 当前模型代码、模型文件状态和索引状态；
- 增强查询当前是否可用及不可用原因。

响应包含 `generatedAt` 和整体 `ready`、`degraded` 或 `unavailable` 状态。每项远程检查上限为 5 秒，不使用上次结果缓存。单项检查失败时返回该项的安全状态和原因代码，其他成功项仍正常返回。

系统状态不包含业务记录数量、日志、堆栈、内部 URL、访问令牌、环境变量或可修改状态的操作。

## 12. 错误处理

### 12.1 Prompt 查询错误

- **事件歧义**：暂停并请用户选择；
- **事件无可靠匹配**：停止数据库分析；
- **增强查询不可用**：披露原因，保留普通搜索结果，不静默声称增强成功；
- **API 或数据库不可用**：停止并说明 Causality 当前不可读；
- **路径被截断**：标记结果不完整，不能把未找到表述为绝对不存在；
- **证据包路径失效**：自动重新查询路径一次；仍失败则停止并说明数据可能已经变化；
- **案例读取失败**：保留已经读取的关系事实，明确写案例证据未加载；
- **外部联网失败**：只取消外部信息章节，不覆盖库内报告。

模型不得用常识、想象或外部内容填补失败的数据库响应。

### 12.2 Resource 错误

静态 Resource 必须始终生成合法内容。系统状态 Resource 对各依赖分别捕获超时、连接和契约错误，并返回部分状态；只有 Resource 自身无法生成符合本地严格 Schema 的 JSON 时才返回 MCP 错误。

错误原因使用固定安全代码，不包含原始响应、SQL、堆栈、令牌或内部连接信息。

## 13. 安全与兼容性

1. 三个分析 Prompt 只编排十个知识和证据工具；
2. 四个 Resource 全部只读，不包含写操作或可执行指令；
3. 原有 15 个工具名称、输入、输出和 annotations 保持兼容；
4. `causality_capture` Prompt 的名称和内容保持兼容；
5. Streamable HTTP 与 stdio 使用同一个 Server 工厂和同一份能力 manifest；
6. 客户端不支持 Prompt 或 Resource 时，核心工具仍可独立调用；
7. 分析结果不会自动变成采集候选或正式数据库记录；
8. 系统状态 JSON 不暴露敏感运行配置。

## 14. 自动化测试

### 14.1 Prompt

- 三个 Prompt 正确注册且无参数；
- 三个 Prompt 包含共享事实、安全和外部信息规则；
- 每个 Prompt 只包含自己的查询流程和输出结构；
- Prompt 明确列出允许与禁止调用的工具；
- 路径、案例、关系和链段限制与设计一致；
- MCP Prompt 与对应 Markdown 字节一致；
- 三个 Skill 是薄启动器且不复制业务规则。

### 14.2 Resource

- 四个固定 URI、名称和 MIME 类型正确；
- 领域规则和采集规则来自 canonical source；

- 响应不包含令牌、内部 URL、堆栈或环境变量。
