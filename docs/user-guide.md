# Causality 用户指南

本指南面向使用自托管 Causality 的用户，覆盖账号登录、日常数据维护、语义查询、CSV
导入导出、MCP 客户端接入和 AI 会话采集入库。生产环境安装、密钥配置和账号管理见
项目根目录的 [`README.md`](../README.md)。

## 1. 启动与页面导航

### 1.1 使用 Docker Compose

首次部署必须先在仓库根目录创建生产 `.env`、启动服务并创建账号。完整步骤见
[`README.md` 的“从 GitHub 部署一个干净系统”](../README.md#从-github-部署一个干净系统)。
已经完成配置的部署可运行：

```bash
docker compose up -d --build --wait
```

默认地址：

| 服务 | 地址 | 用途 |
| --- | --- | --- |
| Web | <http://127.0.0.1:8080> | 日常操作页面 |
| MCP | <http://127.0.0.1:8081/mcp> | 外部 AI 客户端连接 |
| MCP 健康检查 | <http://127.0.0.1:8081/health> | 确认 MCP 进程是否运行 |

Web 和 MCP 默认只监听本机回环地址。API、PostgreSQL 和语义 Worker
不直接暴露到本机网络。

使用管理员在服务器终端创建账号时显示的一次性临时密码登录。首次登录会直接要求
设置新密码，不需要再次输入临时密码。所有账号共享同一套知识库并拥有相同业务权限。

### 1.2 页面用途

| 页面 | 主要用途 |
| --- | --- |
| 原子事件 | 维护抽象、可复用的原子事件 |
| 因果关系 | 维护事件之间有方向的因果关系和案例依据 |
| 具体案例 | 记录真实发生过的具体事件 |
| 因果图 | 从一个中心事件查看受限的局部因果网络 |
| 数据维护 | 手动检查并处理重复、孤立和失效关联 |
| 导入导出 | CSV 数据交换和成功 AI 入库历史 |
| 参数配置 | 语义模型、查询门槛和 MCP 连接配置 |
| 系统状态 | 手动检查 API、数据库和语义 Worker |

左侧导航可以折叠。三个业务列表固定每页 50 条；从详情或编辑页面返回时，会恢复
原页码并定位原记录。

## 2. 建立因果知识

### 2.1 建议录入顺序

1. 在“原子事件”中创建原因事件和结果事件；
2. 在“具体案例”中记录已经发生的真实事件；
3. 在“因果关系”中选择原因事件和结果事件；
4. 填写关系说明，并搜索或新建用于支持关系的具体案例；
5. 保存后在关系详情、事件详情或局部因果图中检查关联。

具体案例也可以先保持独立，之后再关联到一条或多条因果关系。

### 2.2 原子事件

原子事件是从具体事实中抽象出的、逻辑上不可再细分的事件。创建时：

- 名称必须唯一，最长 50 字；
- 说明可选，用于解释事件边界；
- 可以添加多个别名，单项最长 80 字；
- 可以添加多个关键词，单项最长 50 字。

别名适合保存同一概念的不同说法；关键词适合保存领域术语和常用检索词。已有事件
名称不能由 AI 入库流程修改，但可以追加别名、关键词或替换说明。

### 2.3 具体案例

具体案例是一条已经真实发生的事件简短记录，最长 100 字。建议在内容中保留对判断
有帮助的时间、地点和主要事实，但不要把来源 URL、长篇论证或多个独立事件全部塞进
同一条案例。

### 2.4 因果关系与置信度

关系方向始终是“原因事件 → 结果事件”：

- 不允许原因和结果是同一事件；
- 不允许同方向重复关系；
- 允许存在反向关系，保存时会提示反向关系已经存在；
- 删除关系不会删除两端事件或关联案例。

新关系默认以 `10%` 和 0 条案例作为自动计算基准。案例数量增加时，置信度逐次
提高，但每次提高的幅度会降低且不会达到 `100%`；取消案例关联时会相应降低。
手动修改置信度后，手动值和当时案例数成为新的计算基准。

置信度只表示库内记录的因果相关确信程度，不是统计因果证明，也不会替代用户对
案例真实性和关系准确性的判断。

## 3. 搜索与局部因果图

### 3.1 普通搜索

原子事件、具体案例和因果关系三个列表默认执行普通搜索：

- 原子事件：名称、别名、关键词和说明；
- 具体案例：案例内容；
- 因果关系：两端事件名称和关系说明。

普通搜索不依赖语义模型，在 Worker 故障或索引重建期间仍可使用。

### 3.2 增强查询

需要查找同义表达、口语改写或不包含相同关键词的候选时：

1. 打开“参数配置”；
2. 选择一个模型并执行“下载并使用”；
3. 等待模型完成下载、校验、加载和索引；
4. 回到业务列表输入查询词；
5. 点击搜索框右侧的“增强查询”。

增强查询只补充语义候选，不会修改数据。每个模型分别保存增强查询门槛和数据查重
门槛。修改门槛不会重新生成索引。

### 3.3 局部因果图

1. 打开“因果图”；
2. 搜索并选择中心原子事件；
3. 选择双向、下游或上游；
4. 选择 20、50 或 100 个节点上限；
5. 按最低置信度和最少案例数缩小范围。

画布支持平移、缩放、适应画布和临时拖动节点。选择节点会高亮相邻关系和另一端
节点；选择关系会高亮两端节点。按空格打开或关闭右侧检查器，按 `Esc`
清除选择。

## 4. 数据维护

数据检查不会自动执行。需要检查时：

1. 打开“数据维护”；
2. 点击“检查数据”；
3. 查看本次错误、警告、未处理数量和孤立数据统计；
4. 使用严重程度、问题类型和处理状态筛选；
5. 点击问题行的“展开”；
6. 阅读问题描述和处理建议；
7. 有确定处理方案时选择方案并点击“确认处理”；需要人工判断时，先从来源链接进入
   详情处理，再重新执行检查；
8. 不准备处理且希望结束当前快照中的问题时，点击“忽略此问题”。

自动处理和状态更新在同一数据库事务内完成。处理失败时不会留下部分修改。
“忽略此问题”只影响本次检查快照；下一次检查仍满足规则时会重新出现。

## 5. CSV 导入导出

CSV 是 Causality 的人工数据交换路线，与 MCP 的 JSON 入库路线相互独立。

### 5.1 文件格式

文件必须是 UTF-8、无表头、逗号分隔，所有字段都用 ASCII 双引号包裹。支持三类
记录：

```csv
"原子事件","事件名称","事件说明","别名1;别名2","关键词1;关键词2"
"具体案例","案例内容"
"因果关系","原因事件名称","结果事件名称","70","关系说明","具体案例1","具体案例2"
```

字段中可以包含逗号和真实换行。字段内的双引号写成两个双引号：

```csv
"具体案例","某公司公告称：""原材料供应中断""，随后调整生产计划"
```

完整字段约束、转义规则和整文件拒绝条件见
[`README.md` 的“CSV 数据交换”](../README.md#csv-数据交换)。

### 5.2 导入

1. 打开“导入导出 → 文件导入”；
2. 点击“选择文件”并选择 `.csv`；
3. 点击“开始导入”；
4. 等待完成后，页面会自动进入本次导入详情；
5. 在原子事件、具体案例、因果关系和案例关联子标签中检查新增与复用结果；
6. 返回导入历史可查看所有成功批次。

导入只追加数据，不修改已有记录。与数据库严格匹配的数据会复用；CSV
内部完全相同的记录先归并为同一条，不计为“复用”。可以可靠定位的无效行会跳过，
不会保存原始文件和无效内容。

CSV 导入只验证格式和确定性关联，不判断事实真实性、原子性或因果准确性。导入后
应使用“数据维护”检查潜在重复和其他质量问题。

### 5.3 完整导出

1. 打开“导入导出 → 文件导出”；
2. 选择“完整导出”；
3. 点击“数据导出”；
4. 在确认框检查预计导出的事件、关系和案例数量；
5. 点击“导出”，由浏览器选择本地保存位置。

应用只提供导出前数量确认，不监控浏览器保存进度，也不保存导出历史。

### 5.4 筛选导出

1. 选择“筛选导出”；
2. 搜索一个或多个起始事件，逐个从下拉候选中选择；
3. 选择上游、下游或双向；
4. 选择 1–10 层关系深度；
5. 点击“数据导出”并确认数量。

导出范围包含起始事件、深度内关系及其两端事件，以及这些关系关联的全部具体案例。
导出的文件使用同一格式，可以再次导入 Causality。

### 5.5 CSV 安全提示

CSV 全字段双引号只能保证解析正确，不能阻止电子表格软件把以 `=`、`+`、`-`
或 `@` 开头的内容解释为公式。不要用电子表格软件直接打开来源不可信的文件；
需要查看时优先使用不会执行公式的纯文本编辑器。

## 6. MCP 客户端接入

MCP 适合让外部 AI 客户端在对话中查询 Causality，并在受控流程下生成和提交 AI
入库方案。生产使用优先选择 Streamable HTTP；stdio 是源码开发和兼容旧客户端的
备用方式。

### 6.1 获取连接配置

1. 确认 Compose 已启动并登录 Web；
2. 打开“参数配置 → MCP 服务”；
3. 确认状态为“运行中”；
4. 创建一个名称唯一、便于识别的个人令牌；
5. 在令牌所在行点击“复制完整 JSON 配置”。

复制结果：

```json
{
  "transport": "streamable-http",
  "url": "http://127.0.0.1:8081/mcp",
  "headers": {
    "Authorization": "Bearer <个人令牌>"
  }
}
```

在客户端中新建名为 `causality` 的 MCP Server，把以上传输类型、URL
和请求头填入对应字段。不同客户端的最外层配置格式并不统一，可能使用
`mcpServers`、`servers`、图形化设置页面或工作区配置文件；不要机械复制其他客户端
的最外层结构。

个人令牌继承创建账号的完整 MCP 能力：

- 不要提交到 Git、截图公开或发送给他人；
- 可以为不同客户端创建不同令牌；
- 撤销会永久删除指定令牌，该令牌的后续请求立即失效；
- 撤销一个令牌不会影响同一账号的其他令牌。

### 6.2 Streamable HTTP 通用配置示例

如果客户端使用常见的 `mcpServers` 结构，可以按其文档改写为：

```json
{
  "mcpServers": {
    "causality": {
      "type": "streamable-http",
      "url": "http://127.0.0.1:8081/mcp",
      "headers": {
        "Authorization": "Bearer <个人令牌>"
      }
    }
  }
}
```

这里的最外层结构只是示例；应以具体客户端文档为准。协议级检查应能看到 15 个工具、
5 个 Prompt 和 4 个 Resource。客户端界面可能只展示其中的工具。

### 6.3 Codex 专用入口

在 Causality 仓库根目录启动 Codex：

1. 输入 `/mcp`，确认 `causality` 已连接并显示 15 个工具；
2. 输入 `/skills` 查看可用工作流，或者直接使用：
   - `$causality-capture`：采集当前会话并生成受控入库方案；
   - `$causality-analyze-event`：分析一个事件的直接原因或直接结果；
   - `$causality-trace-path`：追踪两个事件之间的有向因果路径；
   - `$causality-review-chain`：逐段审查一条候选因果链；
   - `$causality-infer-outcomes`：推测单个事件可能产生的后续结果；
3. Skill 会读取仓库 `prompts/` 中的同源 Markdown Prompt，再调用 `causality` MCP
   工具。不要尝试把 MCP Prompt 名称直接当作 Codex 斜杠命令。

Codex 的 `/mcp` 页面只负责服务器、鉴权和工具发现；看不到 Prompt 或 Resource 不代表
服务端没有发布。需要完整检查这两类能力时使用 MCP Inspector。Codex 还会读取服务器
初始化响应中的 `instructions`，自动获得最重要的事实边界和受控写入规则。

仓库级 Skill 通过 `.agents/skills` 暴露。Codex 通常会自动发现变更；如果 `/skills`
仍未显示这些入口，重启 Codex 或新建会话。

### 6.4 stdio 兼容入口

源码开发并且 API 已在 `127.0.0.1:3000` 运行时，可以让支持 stdio 的客户端执行：

```json
{
  "command": "pnpm",
  "args": [
    "--dir",
    "/absolute/path/to/causality",
    "mcp:stdio"
  ],
  "env": {
    "CAUSALITY_API_URL": "http://127.0.0.1:3000",
    "CAUSALITY_MCP_TOKEN": "<个人令牌>"
  }
}
```

必须把仓库路径改为本机绝对路径，并提供已创建的个人令牌。它不适合只启动生产
Compose、但未把 API 暴露到宿主机的场景，此时应使用 Streamable HTTP。

### 6.5 使用 MCP Inspector 手工检查

源码开发环境先启动 API，再运行：

```bash
pnpm mcp:inspect
```

Inspector 启动后建议按以下顺序检查：

1. 执行 `tools/list`，确认能看到 15 个工具；
2. 执行 `prompts/list`，确认存在 5 个 `causality_*` Prompt；
3. 执行 `resources/list`，确认存在 4 个 `causality://` Resource；
4. 获取 `causality_capture`，确认返回“Causality 会话采集与入库”规范；
5. 获取 `causality_infer_outcomes`，确认返回“Causality 基于知识库的结果推测”规范；
6. 调用 `search_atomic_events`：

   ```json
   {
     "query": "能源价格"
   }
   ```

   普通搜索无法形成可靠匹配时，可以明确测试增强搜索：

   ```json
   {
     "query": "能源供应趋紧",
     "searchMode": "enhanced"
   }
   ```

7. 从结果复制一个事件 ID，再调用 `get_atomic_event`：

   ```json
   {
     "eventId": "<事件 UUID>",
     "relationLimit": 20
   }
   ```

8. 需要测试局部图时调用 `query_local_causal_graph`：

   ```json
   {
     "centerEventId": "<事件 UUID>",
     "direction": "both",
     "limit": 20,
     "minConfidence": 0,
     "minCaseCount": 0
   }
   ```

写入类工具不应在不了解方案内容时直接调用。完整采集应通过 Prompt 或 Skill
执行，并等待用户明确确认最新方案。

## 7. 使用外部 AI 查询知识库

MCP 连接成功后，可以在客户端中用普通语言提问，例如：

- “在 Causality 中查找与能源供应减少有关的原子事件。”
- “读取这个事件的上下游关系，并列出支持主要关系的具体案例。”
- “从这个中心事件向下游查询 20 个节点，最低置信度 30%，至少 1 条案例。”
- “根据库内关系分析该事件可能产生的直接结果，并区分数据库事实与推测。”

AI 应先使用搜索工具获取稳定 ID，再读取详情、关系案例或局部因果图。MCP
返回的是数据库中已有内容；如果 AI 结合外部网页或自身知识做推测，应明确区分
“数据库记录”和“模型推测”。

应用自身不提供网页搜索。是否能联网，以及如何引用网页来源，取决于外部 AI
客户端和用户授予的工具。

### 7.1 基于知识库推测后续结果

在 Codex 中显式使用 `$causality-infer-outcomes`，或在支持 MCP Prompt 的客户端中选择
`causality_infer_outcomes`。也可以直接提出：

> 使用 Causality 推测“政策利率下降”可能产生的后续结果。

第一版遵守以下固定范围：

- 每次只分析一个起始事件；
- 先普通搜索，不能可靠匹配时再使用增强搜索；
- 只查询下游，默认深度为三层；
- 局部图从20个节点开始，必要时扩展到50和100个；
- 首次最多展示五个候选结果；
- 同一结果最多展示三条路径，每段关系最多展示三个案例；
- 无案例关系仍可参与，但必须标明“无案例依据”；
- 不计算综合证据等级、平均置信度、置信度乘积或结果发生概率。

报告先给出结果摘要，再按候选结果展示路径中每段关系的置信度和案例数。路径最低
置信度只表示路径中数值最低的一段关系，不是结果发生概率。达到节点或路径限制时，
报告会说明结果可能不完整。

用户继续追问某个结果时，该结果会成为新的单一起始事件，再进行一次受限查询。默认只
使用 Causality 数据库；用户明确要求结合网络资料时，外部信息必须放在独立章节，不能
伪装成库内事实。需要把分析发现保存到数据库时，应退出推测流程并重新启动
`Causality Capture`，等待用户审核完整入库方案。

## 8. AI 会话采集与入库

### 8.1 四种工作流入口

根据客户端能力选择入口：

1. Codex：在仓库中显式调用 `$causality-capture`；
2. 其他支持 MCP Prompt 的客户端：显式调用 `causality_capture`；
3. 其他支持 Skill 的客户端：安装仓库中的
   [`.agents/skills/causality-capture`](../.agents/skills/causality-capture)；
4. 客户端不支持以上能力：把
   [`prompts/causality-capture.md`](../prompts/causality-capture.md)
   作为会话规则加载。

斜杠命令和 Skill 都不是 MCP 的通用强制界面。某些客户端可能显示
`/causality_capture`，另一些客户端会显示命令面板、按钮或 Prompt 列表。

### 8.2 发起采集

用户需要明确发起，例如：

> 采集当前会话中与供应链中断主线有关的内容，对比 Causality 数据库并生成完整入库方案。

普通分析、追问或数据库查询不会自动触发采集。采集范围由 AI 自动确定：

- 当前可见会话中存在最近的
  `[Causality-Capture: <historyId>]` 时，只采集该标记之后的内容；
- 没有标记时，从当前可见会话最早内容开始；
- AI 不能读取客户端没有提供的隐藏历史；
- 只提取与用户问题和原因/结果追溯主线直接相关的内容；
- 一次最多处理 50 条原子事件。

### 8.3 自动生成方案

从用户发起采集到首次方案生成之间，AI 应自动连续完成：

1. 提取原子事件、具体案例、因果关系和案例关联候选；
2. 调用 `compare_knowledge_candidates` 一次性对比全部候选；
3. 判断 create、reuse 或 skip；
4. 调用 `prepare_knowledge_changes` 生成完整、不可变、限时有效的方案；
5. 用普通语言展示新增、复用、跳过、事件属性补充、案例关联和预计置信度变化。

内部工具参数使用 JSON；用户看到的应是可读的普通语言，不是 CSV 或大段原始 JSON。

已有数据的修改边界：

- 原子事件名称不可修改；
- 可以为已有事件追加别名、关键词或替换说明；
- 具体案例内容不可修改；
- 已有关系的两端事件和说明不可修改；
- AI 不直接设置置信度，应用根据案例关联变化自动计算。

### 8.4 修改方案和确认

用户可以提出修改，例如：

- “这个原子事件应该复用已有事件，不要新增。”
- “删除这条与主线无关的候选。”
- “将这个表达作为已有事件的别名。”
- “这个案例无法证明关系，跳过案例关联。”

每次修改都必须重新生成一份完整方案，而不是只显示差异补丁。只有用户明确确认
最新完整方案时，AI 才能：

1. 调用 `get_import_plan_status` 确认方案仍可提交；
2. 调用 `commit_knowledge_changes`；
3. 返回实际提交数量和成功标记。

“继续”“看起来可以”“先这样”等含糊表达不构成入库确认。

### 8.5 失败处理

- 数据错误：AI 根据错误中的引用和建议修正候选或决策，重新对比并生成新的完整
  方案，再次等待用户确认；
- 系统错误：AI 说明原因并停止，等待用户修复系统后重试，不能伪造成功；
- 提交响应不明确：使用 `get_import_plan_status` 或 `get_import_result`
  查询，不要重复生成或盲目重复提交；
- 相同方案重复提交是幂等的，不会重复新增数据。

### 8.6 查看 AI 导入历史

成功提交后：

1. 打开“导入导出 → AI 导入历史”；
2. 查看完成时间、采集主题，以及原子事件、具体案例、因果关系和案例关联的变化；
3. 点击“查看详情”；
4. 分别检查原子事件、具体案例、因果关系和案例关联。

只保存成功批次。草稿、取消、校验失败、事务回滚、系统失败、完整会话、网页来源和
AI 推理不会进入历史。

## 9. 常见问题

### MCP 显示“未运行”

```bash
docker compose ps
docker compose logs mcp
curl http://127.0.0.1:8081/health
```

确认 `postgres`、`api` 和 `mcp` 均为 healthy。源码开发时确认根 `pnpm dev`
仍在运行，且 `apps/mcp/.env` 中的 API 地址为 `http://127.0.0.1:3000`。

### 客户端返回 401

个人令牌缺失、格式错误或已经撤销。回到“参数配置 → MCP 服务”查看现有令牌，或创建
新令牌并重新复制客户端配置，然后重新建立连接。

### MCP 能连接但查询失败

先在 Web 的“系统状态”确认 API 和 PostgreSQL；然后检查：

```bash
docker compose logs api
docker compose logs mcp
```

如果只有增强对比不可用，再检查 Semantic Worker 和当前模型索引。普通精确比较和
只读查询不应因语义模型不可用而停止。

### AI 没有显示 `causality_capture`

客户端可能不支持 MCP Prompt，或者不会把 Prompt 显示为斜杠命令。Codex 中使用
`/skills` 或 `$causality-capture`；其他客户端改用 Prompt 列表、命令面板、示例
Skill，或直接加载 [`prompts/causality-capture.md`](../prompts/causality-capture.md)。

### 导入后发现重复数据

CSV 导入只做确定性复用，不做复杂语义审核。打开“数据维护”，确认当前语义模型和
索引可用后重新执行“检查数据”，再处理疑似重复问题。

## 10. 数据安全

- 业务数据、MCP 令牌、AI 成功历史和语义向量保存在 PostgreSQL 命名卷；
- 模型二进制保存在独立模型卷；
- `docker compose down` 不会删除数据；
- `docker compose down --volumes` 会永久删除两个命名卷；
- 每个 MCP 令牌具有所属账号的查询和受控入库能力，只应提供给可信客户端；
- 应用支持多个同权限账号共享知识库，并提供强密码、登录限流、失败锁定和会话管理；
- 正式 Compose 默认只绑定本机回环地址，仓库不包含 TLS 或可直接公网暴露的部署模板；
- 备份说明见 [`README.md` 的“数据持久化与备份”](../README.md#数据持久化与备份)。
